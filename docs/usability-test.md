# 练了么 · 可用性测试脚本（上线前）

## 目的

验证一条核心假设：**训记的老用户能在 90 秒内、零提示地完成第一组记录，并认为比训记更省事。**

如果这条不成立，"1 次点击记一组" 就只是我们自嗨，产品没有存在理由。

---

## 被试

- **5 人**（Nielsen 标准，5 人可暴露约 85% 的可用性问题）
- 招募条件：**正在用训记或曾用过**，每周训练 ≥ 3 次，训练经验 ≥ 3 个月
- 排除：完全新手（不是目标用户，测了会得到错误结论）
- 每人 45 分钟，**单独进行，不互相观摩**

---

## 测试环境

- 用**真机**（目标平台各半），不用原型工具 —— 触感与按钮尺寸是本次测试对象
- 健身房环境模拟：**站立、单手操作、另一只手拿水壶**
- 预置数据：注入 6 周历史记录，让"上次数据"和"建议"有内容可算。
  ✅ **机制已就位**：「我」→「导入备份」支持粘贴导入（见 `docs/screens.md` S10），
  用一份生成的备份 JSON 就能把 6 周历史灌进去 —— 不必等真练 6 周。
- 观察员 1 名 + 记录员 1 名，**不提示、不解释、不救场**

---

## 任务清单

| # | 任务 | 成功标准 | 测什么 |
|---|---|---|---|
| T1 | "你现在到健身房了，开始今天的训练，把第一组记下来" | **5/5 完成，≤ 90 秒，零提示** | 北极星：入口是否真的低 |
| T2 | "刚才那组其实是 65 公斤，改一下" | 4/5 在 15 秒内完成 | 编辑路径是否可发现 |
| T3 | "不小心多点了一组，撤掉" | 4/5 完成，且不是靠重装 | 误触后悔药 |
| T4 | "看看你上周卧推一共推了多少公斤" | 4/5 在 20 秒内完成 | 信息架构是否可找 |
| T5 | "把卧推和划船设成超级组" | **预期多数找不到** | 可发现性：验证"渐进式暴露"的边界 |
| T6 | "把建议的 62.5 改成 60，然后看看下次它还建议什么" | 3/5 能理解系统记住了 | 规则引擎的信任度 |

**T5 是刻意设计的"必败任务"**。目的不是让人找到，而是观察：用户找不到时的反应是"这软件没有"还是"这软件不需要"。前者说明藏得过头，后者说明克制成功。

## 定量指标

> **目标值 vs 实测值分开写**：上表是**目标**（设计意图），实测值由
> `node tool/usability-report.mjs` 算出后粘在下面那张表里（脚本会生成现成的 markdown）。
> 5 场跑完之后，用实测值回头校准 `docs/analytics.md` §1.1 的 55% ——
> 那个数目前是估计值，**这份测试就是校准它的依据**。

| 指标 | 目标 |
|---|---|
| T1 完成率 / 中位耗时 | 100% / ≤ 90s |
| **记录一组的总点击数** | **= 1**（记录员逐次计数，硬约束） |
| 首次训练中打字的次数 | **= 0** |
| 需要滚动才能找到动作的次数 | **= 0** |
| 建议采纳率（T6 中） | ≥ 60% |
| 单场测试后 SUS-lite（4 题简版） | ≥ 80 |

## 访谈提纲（任务后，逐字记录）

1. 你上一次练完腿，第二天是怎么回忆你练了什么的？
2. 你刚才第一次打开这个 App 时，第一反应是什么？
3. 如果现在必须二选一，明天去健身房你带哪个 App？为什么？
4. 刚才有没有哪个瞬间你想找某个功能但没找到？是哪个？
5. 你有没有觉得少了什么，以至于你不想用它？
6. 如果这个 App 收 98 元 / 年，你会买吗？（观察犹豫时长，不只是答案）

> 第 3 题是整个测试的**最终裁判**。前 5 题都可以是礼貌性好评，这一题会逼出真实偏好。

## 通过 / 不通过判据

**通过（可以冻结设计进入开发）**：
- T1 5/5、≤ 90 秒、零提示
- 每组点击数 = 1，首次训练打字 0 次
- ≥ 3/5 在 Q3 选择"带这个 App"

**不通过 → 改什么**：
- T1 超时或需提示 → 砍掉 S2 建议卡，直接进 S4 训练主屏
- T2 找不到编辑 → 主按钮加可见的次要编辑入口（哪怕牺牲一点简洁）
- T4 找不到数据 → 说明"进步"Tab 三块内容的取舍错了，重新分配
- Q3 多数选训记 → **回到定位本身**：说明"更低门槛"不足以让人迁移，需要换楔子（认真考虑社交或教练协作，而不是继续打磨极简）

## 上线后的持续埋点（与测试同源）

| 事件 | 用途 |
|---|---|
| `workout_started` | 漏斗起点 |
| `first_set_logged`（含 `ms_since_launch`） | **北极星**：首次打开 → 完成第一次训练 |
| `set_logged`（含 `tap_count`） | 持续监控"1 次点击"是否被后续迭代破坏 |
| `suggestion_shown` / `suggestion_accepted` | 采纳率 ≥ 60% |
| `suggestion_modified`（含改前改后值） | 规则引擎的失效点在哪 |

> `set_logged.tap_count` 是最重要的一条埋点。**它是"less is more"这条原则唯一的客观守卫** —— 每次发版都应该看它有没有变大。

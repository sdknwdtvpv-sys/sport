## 一、四条红线（先立规矩，再谈钱）

1. **记录训练永远免费**（`PRODUCT.md` §10.3、`monetization-plan.md` 红线）：
   付费墙挡在"完成第一次训练"前面，等于杀掉北极星（≥ 55%）。
   **推论**：付费入口**不出现在**「开练」这条路径上（首页大按钮 → 训练屏 → 总结页），
   只出现在「我 → 设置」与"被锁的那一处"。
2. **数据可携带永远免费**：用户必须能随时导出**自己的全部数据**（CSV 报表 + JSON 备份），
   不因未付费而受限 —— 这是 `PRODUCT.md` §8 的承诺，也是 PIPL/GDPR 意义上"数据可携带"的底线。
   **推论**：Ultra 卖的导出只能是**加工的形态**（年报卡、按动作拆分、Excel/PDF），**不是**"能不能导出"。
3. **不强制注册**：未登录必须能买、能用、能恢复（Apple 5.1.1(v)：核心功能与社交无关时
   **必须允许不登录使用**；`docs/plan-account-login.md` §二-3 已经把这条吵过一遍，结论是"登录可选"）。
   **推论**：权益的**真相在商店收据**上，账号只是"把权益带到别的设备"的便利设施。
4. **不碰自建收款**：iOS 内**只**走 Apple 内购；国内**不**自建支付（要牌照）。
   国内发放权益的合法路径 = 商店各自 SDK（未接）或**兑换码**（本页 §六）。

### 3.2 终身买断与"云"的矛盾（这一条必须先想清）

云备份有**持续成本**，所以"终身 ¥198 含无限云存储"是**卖一张会越来越贵的欠条**。
处置（推荐）：

* **Ultra 终身** = 全部**本地**能力（权益 7/8/9）+ **云备份 1 份 / 8MB**（= 今天免费的额度）；
* **Ultra 订阅**（月/年）= 本地全部能力 **+ 云备份 Plus**（多版本 10 份 / 32MB / 256MB 配额）；
* 会员页把这句话**用一行小字写出来**：「终身版包含哪些、云端容量怎么算」——
  这也正好满足 Apple 3.1.2 要的"说清用户花钱买到什么"。

> 反过来（订阅只卖云）不推荐：本地能力是我们已经做出来的东西，
> 不卖它等于"永远只靠云收钱"，而云恰好是用户最不急的那件事。

### 3.3 试用、优惠与家庭

| 项 | 处置 | 理由 |
|---|---|---|
| 免费试用 | **年订阅 7 天**（Apple introductory offer，类型 = free trial） | 训练 App 的第一次训练在一周内就会发生，7 天足够分辨"我到底会不会用" |
| 首年优惠 | ⏳ 首发**不做**（"首年 ¥68"这类）；等有转化数据再加 | 优惠叠优惠会让会员页多出三行字，而 Apple 要求逐条披露，页面越复杂越容易被拒 |
| 家庭共享 | **订阅开**、终身**开** | 家庭共享是 Apple 免费给的，开了对用户是白得的善意（代价：一份订阅最多 6 人用） |
| 学生价 | 不做 | 没有验证渠道，做了就是"人人都是学生" |
| 促销/打折 | 只在**苹果后台**做（offer code / 促销价），App 里不写"限时" | 写"限时最后一天"这类话，Apple 与国内法规都盯 |

### 3.4 单位经济（先算清再定价）

| 项 | 数 | 说明 |
|---|---|---|
| Apple 分账 | **15%**（小企业计划，年流水 < 100 万美元） | 需要在 App Store Connect 里**主动申请**加入 Small Business Program，别忘 |

## 四、权益的真相在哪：三层 + 一套状态机

```
① 商店收据（Apple / Google）      ← 唯一真相
        ↓ 校验（服务端验签，可选本地缓存）
② 服务端 entitlement（按 account_id / 原始交易号）
        ↓ 下发
③ 本机 entitlements 表（drift）    ← 离线也认，带 7 天宽限
```

三条规则：

1. **未登录也能成为 Ultra**：购买后本地就有权益（商店收据认的是 Apple ID / Google 账号，
   不是我们的账号）。**"恢复购买"按钮是 Apple 硬要求**，位置固定在会员页。
2. **登录后把权益绑到账号**（`auth_session.accountId`，`app/lib/data/db.dart:573`）：
   换手机、重装、跨平台都用它找回来。绑定是**幂等**的（按 `original_transaction_id` 去重）。
3. **服务端判、本机缓存**：本机只缓存"到期时间 + 权益位"，离线时按它放行；
   联网后校准。**接受越狱设备绕过**（老方案已记录这个代价）—— 我们的姿态是"离线优先、不严防"。

### 4.1 状态机（每一态都要有测试）

| 状态 | 触发 | 界面 | 权益 |
|---|---|---|---|
| `trial` | 年订阅试用期内 | 「试用中 · 还剩 N 天」 | 全给 |
| `active` | 订阅有效 / 终身 | 「Ultra · 有效期至 …」/「Ultra · 终身」 | 全给 |
| `grace` | 扣款失败，Apple 宽限期 | 一行提醒：「自动续费没成功，去 App Store 处理」 | 全给（宽限期内**必须继续给**） |
| `billingRetry` | 宽限期也失败，Apple 仍在重试 | 同上，语气更重 | 全给直到 Apple 说停 |
| `expired` | 订阅到期 | 「已到期 · 续费」 | **降级但不删数据**：云多版本停止、只留最新 1 份；本地进阶功能变只读入口可看不可用 |
| `refunded` | Apple 退款通知（`REFUND`） | 同上 | 立即降级；**不再重复退款风控**（第 2 次退款记一笔） |
| `revoked` | 家庭共享被撤 / 撤销购买 | 同上 | 立即降级 |
| `offline-grace` | 本机缓存未过期但联网失败 | 界面**照常显示 Ultra**（不弹任何"验证失败"） | 全给（≤7 天） |
| `offline-expired` | 缓存过期且连不上 | 一行说明 + 「重试」 | 只给免费部分 |

**降级的铁律**：**只减新能力，不删任何用户数据**（云上多版本过期后仍保留最新 1 份；
本机数据一个字都不动）。

> ⚠️ **`grace` 与 `billingRetry` 是"要不要打开"的设置，不是自动就有的**：
> 「Billing Grace Period」（宽限期，可选 3 / 16 / 28 天，按时长档）要在 App Store Connect 里**主动开**，
> 不开的话扣款失败当场就过期；Apple 的**账单重试**（billing retry）则是它自己会做的。
> 落地时两件事都要做：① 在 App Store Connect 打开 Billing Grace Period；
> ② **应用内**也要表态 —— 到期前 3 天给一条本地提醒，别让用户在自己的 App 里"突然变成免费用户"
> 却不知道发生了什么（这同时也是中国大陆"自动续费前 5 日提醒"那条要求的落点，见 §7.2）。

## 六、兑换码：**两条完全不同的路**（这一节最容易做错）

> ⚠️ 先说结论：**iOS 里的"兑换码"只能是 Apple 发的码**。
> 我们自己印的码在 iOS 上解锁功能/内容 = 审核指南 3.1.1 明确不许可的
> "用自己的机制解锁内容或功能（license keys、QR 码…）"。
> 所以"兑换码"这件事要**按渠道拆开**，不能一套实现端到端。

### 6.1 iOS：用 Apple 的 Offer Code（订阅）与 Promo Code

| 项 | 做法（2026-10-10 按 Apple 官方文档核实过） |
|---|---|
| 生成 | App Store Connect 后台（订阅 → Subscription Prices → Offer Codes）**或** App Store Connect API。**v1 不做 API 自动化**：后台建码 + 导出 CSV 就够 1000 人以内的量 |
| 两种码 | **一次性码**：每批 **500–25,000** 个，**最长 6 个月**有效（到期日太平洋时间 0 点失效），从后台下载 CSV 自己分发；**自定义码**（如 `SHOUFA2026`）：可多次兑换、**只能在 App 内兑换**（App Store 里输不了）、不强制有效期，但**每个用户每个 offer 只能兑一次** |
| 名额 | 每个 App **每季度 100 万次兑换**（所有订阅共享）；**每个订阅 SKU 同时最多 10 个生效中的 offer**；⚠️ **offer 一旦创建不能改、也不能重新激活** —— 所以建之前把时长/价格/活动名想清楚（错了只能建新的） |
| 沙盒 | 沙盒码 10–10,000 个、最长 6 个月（iOS 16.3+）—— 上线前先用它把兑换路径走通 |
| 用户怎么兑换 | 会员页「兑换」按钮唤起**苹果自己的兑换面板**：iOS 16+ 用 `AppStore.presentOfferCodeRedeemSheet`（SwiftUI 是 `offerCodeRedemption`），iOS 15 用旧版 `SKPaymentQueue.presentCodeRedemptionSheet()`（Apple 标注 iOS 14–18，16 起建议换新 API）。**Apple 明确要求"不要自己做兑换 UI"** |
| 版本门槛 | 订阅的 offer code 从 **iOS 14.2** 起（我们最低 iOS 15.0 ✅）；消耗型/非消耗型/非续期订阅从 **iOS 16.3** 起 —— 所以**终身版（非消耗型）的码只能在 iOS 16.3+ 兑换**，这条要写进运营手册 |
| 绑定与追踪 | 兑换后的订单带 **`offer_code_ref_name`**，能通过 App Store Server API / Notifications V2 拿到 → 我们据此知道"这单是哪个活动发的码"（比"发出去多少"有用得多） |
| 界面文案 | 按钮写「兑换码」，但**必须**唤起苹果面板；**自己画输入框收我们印的码 = 3.1.1 明确的违规**（原文把"license keys、QR 码"都点名了） |
| 证据留档 | 每次发放记一笔（谁、多少、哪个活动、失效日）—— 审核问起来能答；`offer_code_ref_name` 回填到运营记录里 |

> ⚠️ **Promo Code 与 Offer Code 不是一回事**：Promo Code 只能用来**免费获得 App 本体**（评测/赠送），
> 每个平台版本最多 100 个、4 周有效、兑换后不能评分；**它不能给内购/订阅发码** ——
> 赠会员只能用 **Offer Code**。这两个名字在运营话术里很容易混，写进手册时分开写。

### 6.2 国内安卓 / 官网 / 私域：**自建兑换码**

国内安卓商店没有统一内购通道（各家 SDK 各自为政），**兑换码是国内唯一能快速把所有渠道收进来的方式**：
淘宝/微店卖卡密、公众号活动发码、客服补偿、线下收款后发码。

| 项 | 设计 |
|---|---|
| 码形状 | `LMU-XXXXX-XXXXX-XXXXX`（Crockford Base32，去掉 `I/L/O/U` 易混字符）+ 1 位校验位；**≥ 80 bit 熵**（照 `app/lib/backup/recovery_code.dart` 那套现成实现的风格） |
| 生成本质 | 服务端生成 → **只存 SHA-256 哈希**（明文只在生成那一刻返回一次，后台导出给运营） |
| 核销 | **在线核销**（`POST /v1/billing/redeem`），要登录（用 `auth_session.accountId`），一次性、绑账号、写 `billing_events` 审计 |
| 权益形态 | ① 时长码（+30/+365 天 Ultra 订阅）；② 终身码（= Ultra 终身）；③ 云端扩容码（+1 年云 Plus） |
| 防滥用 | 见 6.4 |
| **iOS 上怎么体现** | 用户在国内渠道买过 → 在 iPhone 上**登录同一账号** → 权益**自动生效**（这属于 Apple 允许的 **Multiplatform Services**：可以"访问在别处已购的内容"，但 **iOS 界面里不能有"去别处买"的引导，也不能有自建码输入框**） |

> 这条边界很细，落地时用**平台分支**硬保证：自建码入口只在 `!Platform.isIOS` 时渲染
> （并且**要有测试**：`debugDefaultTargetPlatformOverride` 到 iOS 时不渲染输入框 —— 见 §九）。

### 6.3 交叉表：哪种码在哪合法（**照这张表施工**）

| 渠道 | Apple IAP | Apple Offer Code | 自建码 |
|---|---|---|---|
| iOS App | ✅ 唯一允许的收款 | ✅ 允许（就是苹果的码） | ❌ **不提供入口**（但其他平台买的权益可登录后生效） |
| Android（Play） | ✅ **必须**用 Play Billing（政策原文：Play 分发的 App 收"访问应用内功能/数字内容"的钱，**必须**用 Play 的结算系统） | —（Play 自己的 **Promo Code**：一次性商品每季最多 500 个；订阅每季每产品最多 10,000 个一次性码；自定义码**仅订阅、仅 App 内兑换、且只给从未订阅过的新用户**） | ❌ **同样违规**：Play 分发版里用自建码解锁数字内容 = 与 Apple 同构的违规。**Play 版不放自建码入口** |
| 国内安卓商店 | ⏳ 各家 SDK（未接） | ❌ | ✅ **主渠道** |
| 官网 / 私域 / 线下 | ❌ | ❌ | ✅ |
| 客服补偿 | — | ✅ iOS 用这个 | ✅ 国内用这个 |

### 6.4 防滥用参数（自建码）

| 面 | 参数 | 说明 |
|---|---|---|
| 猜码 | 80 bit 熵 + 在线核销限速 | 在线核销 = 猜错也要打服务器，天然可限速 |
| 限速 | 每 IP 20 次/小时、每账号 5 次/小时、连续 10 次失败**锁 1 小时** | 与 `auth.selftest` 里验证码限速同一套写法 |
| 一码一用 | `redeem_codes.used_by` 唯一写入（事务） | 并发同码只成功一次（要有并发测试） |
| 绑定 | 一次性绑定账号，**不可转移** | 转移 = 二手市场，不做 |
| 撤销 | 后台一条命令作废（未核销的） | 印刷错误/活动取消时用 |

| 有效期 | 生成时可选（默认 2 年） | 活动码设短，客服补偿码设长 |

### 8.4 依赖与产物

* `app/pubspec.yaml` 加 `in_app_purchase`（官方）。**不引第三方变现 SDK**（RevenueCat 之类）：
  它会把购买数据送到第三方（与"默认不收集"冲突），还要抽成。
* Excel(.xlsx) 若要真做，需要新依赖 —— **建议 v1 不做 xlsx**：年报卡（PNG，复用分享卡管线）+ 按动作 CSV 已经够，
  少一个依赖就少一处审核与合规面（§十三 拍板项 4）。
* App Store Connect：建 3 个商品 + 1 个订阅组 + 试用；申请 Small Business Program。
* Google Play：建 2 个订阅 + 1 个一次性商品（若要上 Play 内购）。

## 十一、上架节奏：首版带不带内购（要你拍板）

| 方案 | 好处 | 代价 |
|---|---|---|
| **A. 首版就带 Ultra** | 首波流量是唯一一次免费曝光，转化最好；商品可与版本一起送审 | 上架要多等内购商品审核 + 政策/商店表单改动；首版被拒的面变大（多一类拒审理由） |
| **B. 先免费上架，v1.1 上 Ultra** | 上架最快、最稳；先拿真实留存数据再定价 | 首月没有收入；v1.1 要重新走一次审核（但那次只审增量） |

**我的推荐：看你的上架日期**——
* 上架日期在 **2 周外** → **A**（一次到位，首波流量别浪费）；
* 上架日期在 **1 周内** → **B**（先上去，Ultra 用 M1 的"假开关"先把界面做出来，v1.1 打开真内购）。

⚠️ 不管选哪个，**M1 与 M3 的服务端部分可以并行做**（M1 不依赖商店账号）。

## 十二、风险与对策

### 12.1 审核被拒（按概率排）

| # | 拒审理由 | 预防 |
|---|---|---|
| 1 | **"用自己的机制解锁功能"**（我们自己画输入框收自建码） | iOS 只走 Apple 兑换面板；自建码入口平台分支 + 判据 3 |
| 2 | 3.1.2 披露不全（缺条款/隐私链接、没写自动续费） | `paywall_copy_test` 逐条断言（判据 2） |
| 3 | 站外购买引导（"官网更便宜"、客服话术写进 App、文案暗示） | 全仓 grep 审一遍文案；客服话术只放网页/邮件 |
| 4 | 未登录不能用 / 未登录不能恢复 | 判据 4 |
| 5 | 价格与商店不一致（写死价格） | 价格取自商品对象（判据 2） |
| 6 | "未来功能"当卖点 | 会员页只写当下清单 |
| 7 | 引导好评/虚假紧迫（"限时最后一天"） | 文案红线：不写时间压力 |
| 8 | 订阅必须能"取消"（Apple 也要） | 「管理订阅」入口 + 政策文案 |
| 9 | **2.3.2** 元数据里没说清哪些功能要另外付费 | App 描述 / 截图写明 Ultra 含什么（§7.1 第 10 条） |
| 10 | 审核时把付费藏起来、过审后打开（3.1.1 + 2.3.1，可能封号） | 不做隐藏开关；M1 的假开关只在 `assert` 下存在且 release 包里没有（判据 13） |
| 11 | 缺"恢复购买"或点不动 | 会员页固定 key `restore-purchases`，测试断言可见（判据 14） |

### 12.2 技术与运营

| 风险 | 处置 |
|---|---|
| 越狱绕过本地校验 | 接受（离线优先的必然代价，老方案已记录）；服务端只做"便利同步"，不做"必须在线" |
| 同一账号绑多个 Apple ID 的订阅 | 按 `original_transaction_id` 去重；权益取**最长到期**；永久一旦绑定不退 |
| 终身买断被当成"永久云" | 会员页写清（§3.2），服务端配额按"订阅/终身"分支给 |
| 自建码被薅（活动泄漏） | 限速 + 一次性 + 批量作废 + 活动码短有效期（§6.4） |
| **Offer Code 建错了没法改** | `offer` 一旦创建**不可编辑、不可重新激活**（只能新建一个）；所以：建码前把活动名/时长/价格想清楚，先建 10 个沙盒码走通流程再建正式批次；每个活动留一条运营记录 |
| 云成本失控（有人狂传大备份） | 单份 32MB / 账号 256MB 配额 + 保留 10 份（服务端强校验，不只靠客户端） |
| 退款后用户数据被删的投诉 | 降级**永不删数据**（§4.1 铁律 + 判据 8） |

### 12.3 产品（最要紧的一条）

| 风险 | 处置 |
|---|---|
| **付费入口拖低"首次训练完成率"（北极星）** | 付费入口**只在**「我 → 设置」与被锁的那一处；首页/训练路径零出现（判据 5）。上线后盯一周：若首练完成率下降 > 2 个百分点，就把会员页从设置页的**第一行**降到最下面 |
| 免费版被"阉割感"伤到口碑 | 免费版仍然是**完整可用的记录工具**（红线 1、2）；Ultra 卖的是"更省心"，不是"能用" |

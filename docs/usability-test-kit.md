# 练了么 · 可用性测试现场工具包

> 判据与通过/不通过标准见 `docs/usability-test.md`。本文是**现场照着做就行**的执行手册。
> 目标只有一个：验证"训记老用户能在 90 秒内零提示完成第一组记录，并认为比训记省事"。

---

## 0. 现场物料清单

| 物料 | 说明 |
|---|---|
| 真机 2 台 | iOS 1 + Android 1，装好待测包。**不要充电线牵着**，用户要站着单手操作 |
| 秒表 2 个 | 一个记任务耗时，一个记 T1 |
| 本工具包打印件 | 任务卡（裁成单张）、观察员记录表（每人 1 份）、口播稿 |
| 水壶 1 个 | 让用户另一只手拿着，模拟真实健身房 |
| 报酬 | 现金或转账，测试结束时当场给 |
| 充电宝 | 4 台设备轮转，别在中途没电 |
| 纸笔 | 观察员用，比打字快 |

**场地**：不要在办公室工位。最好找一个能站着、有点噪音的地方（健身房大堂、商场休息区）。环境太安静会让用户行为失真。

## 1. 被试招募筛选问卷

电话/微信筛人时逐条问，**不要提前告诉对方要测什么功能**。

| # | 问题 | 用途 |
|---|---|---|
| 1 | 最近 3 个月，你平均每周练几次？ | **排除 < 3 次**（不是目标用户） |
| 2 | 你现在怎么记录训练？纸笔 / 备忘录 / 训记 / 其他 App / 不记 | 需要"有记录习惯" |
| 3 | 训记你听说过吗？下载过吗？现在还在用吗？ | **配额用**，见下 |
| 4 | 训练时会戴智能手表吗？ | 记录，用于解释行为差异 |
| 5 | 训练多久了？ | **排除 < 3 个月** |
| 6 | 训练计划是自己排的，还是跟教练/跟课程？ | **至少 4 人必须"自己排"** |
| 7 | 平时用 iPhone 还是安卓？ | 配额 |

### 配额（共 5 人）

- **3 人**：训记现存用户（正在用）
- **2 人**：训记流失用户，或仍用纸笔/备忘录的记录党
- iOS 3 人 / Android 2 人
- 性别不限，但必须记录，因为结果解释时要考虑

### 必须排除

- 健身教练、体育专业从业者 —— 他们不是目标用户，视角会严重偏离
- 产品经理、设计师、研究员 —— 会过度分析并给出"设计意见"而不是真实行为
- 完全新手 —— 测了会得到错误结论，本产品不服务他们

## 3. 主持人口播稿（逐字，照读）

### 开场（3 分钟）

> "谢谢你今天过来。我想了解的是一款健身记录 App 好不好用。
>
> 先说清楚：**我们测的是这个 App，不是你**。所以没有对错，也没有你'应该'怎么做。
>
> 过程中请尽量像你平时训练那样操作，**不要为了帮我而特意去找某个按钮**。如果某个地方你顺手就点了，那就点；如果你想找什么但找不到，也不用勉强。
>
> 我会请你做几个任务，做完之后我们聊两句。**我不会中途教你**——所以如果你卡住了、犹豫了、或者心里觉得'这里不对劲'，请直接说出来，那正是我最想知道的东西。
>
> 现在请站起来，另一只手拿住这瓶水，就当我们已经在健身房了。"

### 每个任务前（只说一次，照读）

> "这是一张任务卡，请你按上面的描述做一遍。**用你自己的方式，任何方式都可以。**"

发卡，然后**闭嘴**。

### 用户沉默/卡住时

- 沉默 **30 秒**以上且明显卡住 → 只说一句：
  > "你现在在想什么？"
- **绝不指路**，绝不说"你试试上面那个"。

### 任务后追问（照读，注意顺序）

1. "刚才那个地方，你当时在想什么？"
2. "你当时期望发生什么？"
3. "如果用你自己的话说，这个按钮是干什么用的？"

### 绝对禁止的提问

- ✗ "你觉得这个设计好不好？"（诱导 + 社交礼貌，答案无价值）
- ✗ "是不是比训记方便？"（直接污染核心结论）
- ✗ "你会用这个 App 吗？"（口头承诺不可信，要看 Q3 的**选择**）

## 4. 任务卡（按此裁成单张）

> ⚠️ **这 6 张卡的原文以 `usability/tasks.json` 为准** —— 那份文件是唯一事实源，
> 同时存着记录表用的短名与 `docs/usability-test.md` 用的判定标准。
> 2026-10-01 之前这一节与 `usability/记录表.md` 的 **T3 / T4 / T5 内容不一致**
> （含那个刻意必败的 T5），而 `tool/usability-report.mjs` 只认 id、抓不到 —— 已改齐并由
> `tool/check-usability-tasks.mjs` 守着。**改任务请改那一份**，然后跑它。

**T1**
> 你刚走进健身房，准备开始今天的训练。
> 请把**第一组**记录下来。

**T2**
> 刚才那一组其实是 **65 公斤**，请你改过来。

**T3**
> 你不小心**多点了一组**，请把它去掉。

**T4**
> 你想知道自己**上周卧推一共推了多少公斤**，请查一下。

**T5**
> 你想把**卧推和划船连着做**，当成一个超级组，请设置好。

**T6**
> App 建议你这次推 **62.5 公斤**，但你想推 **60**。
> 请改成 60，然后**完成这一组**。

> T5 是**刻意设计的必败任务**。目的不是让人找到，而是观察找不到时的反应是"这软件没有"还是"这软件不需要"——这是验证"渐进式暴露"尺度的唯一方法。

## 6. ★ 对照环节：让他用自己的训记做同一件事（40 分钟处，务必做）

这是整个测试里**唯一能直接验证核心假设**的一步，不要因为时间紧就砍掉。

> "接下来我想看看你平时怎么记录。请用**你自己手机上的训记**，把你今天的第一组记下来。
> 就像平时一样。"

**同时用同一张 5.2 的表计数、同一个秒表计时。**

| 指标 | 练了么 | 训记（用户自己手机） | 差值 |
|---|---|---|---|
| 冷启动到第一组记录（秒） | | | |
| 记录一组的 tap_count | | | |
| 打字次数 | | | |
| 滚动次数 | | | |

> **判据（2026-10-01 补上 —— 这一节号称"唯一能直接验证核心假设"，之前却没有阈值）**：
>
> * **记录一组的 `tap_count` 差值 ≥ 2 次** 才算"明显更省事"（本品更少）；
> * **冷启动时间差 < 5 秒不算差异** —— 同一个人、同一台机器，5 秒内是噪声，
>   拿它当"更快"是自欺；
> * 两个条件**必须同时**满足才算这一节通过（写进 `docs/usability-test.md` 的通过判据）。
>
> 如果差值不是明显有利于本品，**核心假设就不成立**，不要用"用户不熟练"来解释——
> 用户对训记也未必熟练。

> **SUS-lite 那 4 题 2026-10-01 删掉了。** 原先 §7 给它留了一格时间，`tool/usability-report.mjs`
> 里也有目标值 `susLite: 80`，但**题项与计分公式全仓不存在**，而且脚本的判据是"没填就不判" ——
> 一个永远不生效的闸门。4 题简版的信度也撑不起"≥ 80"这条线。**删掉比补一套题更诚实**；
> 现在这一场唯一的最终裁判是下面的 Q3。

## 7. 现场流程（45 分钟）

| 时间 | 环节 |
|---|---|
| **开场前** | 装包 → **导入预置历史**（见下）→ 杀掉 App 冷启动一次 |
| 0–3 | 欢迎、知情同意、开录音 |
| 3–6 | 口播稿 + 器材确认（站起来、单手持机、拿水壶） |
| 6–12 | 冷启动（**全新安装状态**）→ T1，计时 + 计数 |
| 12–20 | T2 – T6 |
| 20–30 | 访谈提纲 6 题（逐字记录） |
| 30–38 | **对照环节**：用他自己的训记做同一件事 |
| 38–43 | Q3 关键选择（**整场唯一的最终裁判** —— SUS-lite 那 4 题 2026-10-01 删掉了，见 §6 末尾） |
| 43–45 | 付报酬、致谢、提醒不要对外透露内容 |

### 开场前必须做的一件事：导入预置历史

`usability/preset-6-weeks.json`（**生成的，不要手改**）让被试看到的不是一台空机：
首页有"上周练了 2 次"、建议卡有"上次 3 组 · 60kg×10"，**T6 的建议值真的就是 62.5kg**。

```bash
node tool/preset-history.mjs --write    # 跑测试当天重新生成（日期相对"今天"算，不刷新会过期）
node tool/preset-history.mjs --check    # 与生成器逐字节比对；放太久了它会提醒你重新生成
```

刷新 → 把文件内容发到测试机上 → 长按全选复制 →
「我 → 数据与备份 → 导入备份 → 从剪贴板粘贴」→ **杀掉 App 重开**。

> 这份数据不只是"随便造六周"：它被三条不变量钉着 —— **今天轮到胸**（所以最近一次训练是腿）、
> **真引擎对卧推算出 62.5kg**（3 组 × 10 次 @ 60kg ⇒ 加重 2.5）、
> **T4 的答案是 1800kg**（近 7 天卧推容量）。生成器自检和 `verify.sh` 都会核这三条。
> 细节与"为什么是 10 次不是 8 次"写在 `tool/preset-history.mjs` 的文件头。

## 8. 本场必须拿到的 7 个数字

收工时如果这 7 个数缺任何一个，这场测试就白做了。

| # | 数字 | 目标 |
|---|---|---|
| 1 | T1 完成率 | 5/5 |
| 2 | T1 中位耗时 | ≤ 90 秒 |
| 3 | **记录一组的中位 tap_count** | **= 1** |
| 4 | 首次训练全程打字次数 | 0 |
| 5 | 需滚动找动作次数 | 0 |
| 6 | T6 中"采纳建议 / 手改" | 记录，不看目标 |
| 7 | **Q3「明天去健身房带哪个 App」选本品的人数** | ≥ 3/5 |

**收工后不要手算**：

```bash
node tool/usability-report.mjs --template > usability/sessions/P1.json   # 每人一份
node tool/usability-report.mjs                                           # 7 个数字 + 通过/不通过
```

它会替你算中位数、对着上表逐条判，并在**分项加总 ≠ 合计 / 标了完成却没耗时 / 缺 T1**
这类抄错上直接报错 —— 手抄最容易出、又最不容易被发现的正是这几类。
输出的 markdown 块直接粘进 `docs/usability-test.md` 的「定量指标」一节。

## 9. 主持人常见错误（每次复盘对照）

1. **提示**："你试试长按那里" —— 一句话就毁掉一个数据点
2. **辩解**："这个是给专业用户设计的" —— 用户听到的是"你不够专业"
3. **诱导**："是不是比训记方便？" —— 直接污染最重要的结论
4. **问设计意见而不是问行为** —— 用户会给礼貌性好评，行为数据才是真的
5. **被试卡住时抢手机** —— 那一刻的表情和原话才是最值钱的信息
6. **让两个被试互相观摩** —— 第二个人会模仿第一个人的操作，两个数据点变一个
7. **测试前介绍产品** —— 用户会照着你的介绍去找功能，测的就成了你的讲解能力

> 本文是**现场照着做就行**的执行手册。正式版的判据与通过/不通过标准见 `docs/usability-test.md`。
>
> **本包有两套，别混用：**
>
> * **§A 熟人短测** —— 2026-10-05 拍板：`tap_count` 的目标值（门槛）**由它定**。
>   3–5 个熟人、每人 5 分钟、只取点击数分布，**半天做完**。⚠️ 它**替代不了**正式测试。

> 正式版要验证的那条原始目标（**不是短测的目标**）：训记老用户能在 90 秒内零提示

## A · 熟人短测（把 `tap_count` 的门槛定出来，半天）

> **2026-10-05 拍板**：`tap_count` 的目标值改由**熟人在真机上短测**定 —— 3–5 个熟人、
> 每人 5 分钟、只取点击数分布，**半天做完就能定门槛**。原内部纪律「校准前不允许上架」
> **作废**，改由「短测完成即可定门槛」。

### A0 · 它是什么、不是什么（先读，写结论时照这句写）

* 它是**一次小样本标定**，只回答一个问题：**记录一组要几下**。产出一个门槛数字，仅此而已。
* 它**不是可用性测试**：不测"90 秒内能不能零提示完成"、不问偏好、不做对照、不跑 T2–T6，
  也不产出 §8 那 7 个数字。
* 它**替代不了** §0–§10 那套 5 人测试。n=3–5 定出来的中位数只够当**第一次标定**；
  **不许**写成"验证通过""可用性合格""用户更喜欢"。
* 上面那几条仍只有正式测试能回答，所以 §0–§10 **仍建议做**，只是**不再阻塞上架**。

### A1 · 招谁（3–5 个熟人）

| 要 | 不要 |
|---|---|
| 手边有自己的手机、能独立操作（不需要懂训练计划） | **健身教练 / 体育专业从业者** —— 视角与手感都偏离（与 §1 同一条理由） |
| 有健身习惯、平时会记训练（纸笔 / 备忘录 / 训记都行） | **本项目参与者** —— 开发、记录员、看过设计稿或任务卡的人；他们知道按钮在哪，数字只会偏小 |
| 一次只测一个人，**不互相观摩** | 互相看过操作的两个人 —— 第二个会照着第一个做，两个数据点变一个 |

* **不需要**：训记用户配额、iOS/Android 配额、报酬、录音、场地。那些是**正式测试**的规格（§0 / §1）。
* **刻意不筛配额**：不要求"训记用户 / 训记流失用户"的配比、不要求机型配比、不要求训练经验 ≥ 3 个月 ——
  短测取的是"点了几下"这种机械量，不是偏好与理解。
  代价照说：不健身的人在"要不要改重量"这一步上会与目标用户不同 ——
  所以**只在同一批人内部比分布**，不要拿它去估计目标用户的比例。
* 3 个人能出数，5 个人更稳；**少于 3 个人不要定门槛**（那不是分布，是一个人的手感）。

### A2 · 多久、怎么起跑（每人 5 分钟）

| 项 | 口径 |
|---|---|
| 每人 | **5 分钟**（含递手机、说那句话、看着他点完）；3–5 人合计**半天** |
| 场地 | 站着、单手更好（§0 的"另一只手拿水壶"）；短测**不强制**，做不到就坐着 —— 但当天要在结论里注明（场地会改变点击行为） |
| 起跑状态 | **冷启动**：杀掉 App 再打开，停在首页；期间**不告诉他大按钮在哪、不给任何提示** |
| 预置历史 | 每人开始前按 §7 重导一次 `usability/preset-6-weeks.json`（当天先用 `node tool/preset-history.mjs --write` 重新生成，导入是幂等的），再杀进程冷启动 |
| 任务 | 只做 **§4 的 T1**（原话的事实源是 `usability/tasks.json`）。把卡递给他，然后闭嘴 |

> **为什么每人之前要重导一次**：预置历史决定"建议值有没有内容"。
> 导入是 upsert（按 id 落库，见 `app/lib/features/profile/backup_source.dart` 的注释），
> 所以**同一份预置导两遍不会翻倍**；但它也**不会抹掉前一个人记下的那组**。
> 那组要是改变了"建议值 → 要不要改重量"这一步，两条路：① 换一台机子；② 就在表里注明
> "这一位的建议值受前一位影响" —— 别事后假装没有。

### A3 · 只取什么（别的都不采）

只取 **`tap_count` 分布**，也就是这四个数：

1. **每人"第一次记录一组"的总点击数** —— 端到端口径，哪几次点击计入以 `docs/analytics.md` §3
   那张表为准（导航 / 选动作 / 换动作 / 长按 / 步进 / 确定 / 大按钮；休息跳过、返回、滚动不计）。
2. **每个步骤各点了几下** —— 按 §5.2 那张"一个正字 = 1 次点击"的分来源表数。
3. **有没有哪一步超过 3 次点击** —— `PRODUCT.md` §1 的裁判规则就是"超过 3 次点击判负"；
   超了的那一步，就是"先修哪一步"的答案。
4. **n / 中位数 / 最大值** 这三个派生数（怎么用见 A5）。

**不采**：不访谈、不问"好不好用"、不录音、不录屏、不装任何监控、不跑 T2–T6、不记真实姓名。
短测唯一值钱的产出就是那张点击数表 —— 其余都是给自己找活干。

|---|---|---|---|---|---|---|---|
| S1 | ☐ | | | | | | |
| S2 | ☐ | | | | | | |
| S3 | ☐ | | | | | | |
| S4 | ☐ | | | | | | |
| S5 | ☐ | | | | | | |

* 填表规则与 §5.2 一样：**一个"正字" = 1 次点击**，只数"为了产生这一组"发生的点击。
* **总点击要自己再手加一遍**（分项之和），别只写一个总数 —— 纸面上最常见的错就是这里。
* 有条件的做一次**交叉核对**：用「隐私与关于 → 导出统计事件」把 `set_logged.tap_count` 导出来
  （入口与用途见 `docs/plan-stage3-5.md` A1）。**两边对不上时先怀疑真机口径，不要先怀疑手抄** ——
  手抄错看得见，口径错看不见。
* 原始表留在现场；**不要把它整张贴进 `docs/analytics.md`**（那里只放门槛与分布摘要）。

### A5 · 怎么定门槛（用分布定，不是拍一个数）

1. 把 n 个人的"总点击"排序：**中位数**就是 `tap_count` 中位数的第一次标定值。
2. 门槛写成「**多数人 ≤ N 次**」：中位数落在哪个整数，就把那个整数写成门槛。
   例：5 个人的总点击是 2 / 2 / 3 / 3 / 4 → 中位数 3 → 中位数门槛写 **3**。
3. 中位数是 .5（n 为偶数）时：门槛取**向上取的整数**（宽松侧，例如实测 2.5 → 门槛 3），
   但**实测值（2.5）必须一并写进 `docs/analytics.md` §3 的注释** ——
   §3 下面那条门禁比的是"与上一版相比有没有上升"，实测值丢了就没法比。
4. P90 / P99：**n=3–5 算不出可信分位数**。填法写死 —— P90 填**本次最大值**并注明
   "小样本最大值，不是分位数"；P99 **留空**，等真实上报数据。**不许**用插值假装算出 P90。
5. **超线先修**：分布里只要有一步 > 3 次点击（`PRODUCT.md` §1 那条红线），
   就先修那一步，**不要**把"多数人做不到"的数字写成目标值。
6. 结论只写事实：`n=4，总点击 2 / 2 / 3 / 4，中位数 2.5，门槛取 3`。**不写**"体验良好"
   "达到目标""通过测试" —— n=3–5 撑不起这三句话。

### A6 · 做完往哪写（一处一处，别漏）

| # | 写进哪 | 写什么 |
|---|---|---|
| 1 | `docs/analytics.md` §3 的「目标（**待校准**）」表 | 中位数 / P90 / P99 三行填上门槛（P90 注明是小样本最大值、P99 留空）；**同时去掉"待校准"的标记**，并把 §3 里"校准办法 = 按本包招 5 人测试、数字到手之前不允许发布"那几句改成短测口径 |
| 2 | `docs/analytics.md` §3 表下的注释 | 原始分布（n、逐个总点击、中位数、最大值）与测量日期 —— 门槛要能追溯到这张表 |
| 3 | `docs/your-todo.md` / `docs/release-checklist.md` | 那两份里"校准前不允许上架"一类说法，由持有它们的人跟着改（本页不代抄） |

* **门槛只写一处**：`docs/analytics.md` §3。别在本文件、`ROADMAP.md` 或别处再抄一遍数字 ——
  这个仓库的规矩是一份事实只写一处，别处给指针。
* §A4 的记录表与导出物**不进仓库**；§3 只收门槛与分布摘要。
* §8 那 7 个数字**不因此免做**：它们属于正式测试，仍建议做。

## 1. 被试招募筛选问卷

电话/微信筛人时逐条问，**不要提前告诉对方要测什么功能**。

| # | 问题 | 用途 |
|---|---|---|
| 1 | 最近 3 个月，你平均每周练几次？ | **排除 < 3 次**（不是目标用户） |
| 2 | 你现在怎么记录训练？纸笔 / 备忘录 / 训记 / 其他 App / 不记 | 需要"有记录习惯" |
| 3 | 训记你听说过吗？下载过吗？现在还在用吗？ | **配额用**，见下 |
| 4 | 训练时会戴智能手表吗？ | 记录，用于解释行为差异 |
| 5 | 训练多久了？ | **排除 < 3 个月** |
| 6 | 训练计划是自己排的，还是跟教练/跟课程？ | **至少 4 人必须"自己排"** |
| 7 | 平时用 iPhone 还是安卓？ | 配额 |

### 配额（共 5 人）

- **3 人**：训记现存用户（正在用）
- **2 人**：训记流失用户，或仍用纸笔/备忘录的记录党
- iOS 3 人 / Android 2 人
- 性别不限，但必须记录，因为结果解释时要考虑

### 必须排除

- 健身教练、体育专业从业者 —— 他们不是目标用户，视角会严重偏离
- 产品经理、设计师、研究员 —— 会过度分析并给出"设计意见"而不是真实行为
- 完全新手 —— 测了会得到错误结论，本产品不服务他们

## 3. 主持人口播稿（逐字，照读）

### 开场（3 分钟）

> "谢谢你今天过来。我想了解的是一款健身记录 App 好不好用。
>
> 先说清楚：**我们测的是这个 App，不是你**。所以没有对错，也没有你'应该'怎么做。
>
> 过程中请尽量像你平时训练那样操作，**不要为了帮我而特意去找某个按钮**。如果某个地方你顺手就点了，那就点；如果你想找什么但找不到，也不用勉强。
>
> 我会请你做几个任务，做完之后我们聊两句。**我不会中途教你**——所以如果你卡住了、犹豫了、或者心里觉得'这里不对劲'，请直接说出来，那正是我最想知道的东西。
>
> 现在请站起来，另一只手拿住这瓶水，就当我们已经在健身房了。"

### 每个任务前（只说一次，照读）

> "这是一张任务卡，请你按上面的描述做一遍。**用你自己的方式，任何方式都可以。**"

发卡，然后**闭嘴**。

### 用户沉默/卡住时

- 沉默 **30 秒**以上且明显卡住 → 只说一句：
  > "你现在在想什么？"
- **绝不指路**，绝不说"你试试上面那个"。

### 任务后追问（照读，注意顺序）

1. "刚才那个地方，你当时在想什么？"
2. "你当时期望发生什么？"
3. "如果用你自己的话说，这个按钮是干什么用的？"

### 绝对禁止的提问

- ✗ "你觉得这个设计好不好？"（诱导 + 社交礼貌，答案无价值）
- ✗ "是不是比训记方便？"（直接污染核心结论）
- ✗ "你会用这个 App 吗？"（口头承诺不可信，要看 Q3 的**选择**）

## 6. ★ 对照环节：让他用自己的训记做同一件事（40 分钟处，务必做）

这是整个测试里**唯一能直接验证核心假设**的一步，不要因为时间紧就砍掉。

> "接下来我想看看你平时怎么记录。请用**你自己手机上的训记**，把你今天的第一组记下来。
> 就像平时一样。"

**同时用同一张 5.2 的表计数、同一个秒表计时。**

| 指标 | 练了么 | 训记（用户自己手机） | 差值 |
|---|---|---|---|
| 冷启动到第一组记录（秒） | | | |
| 记录一组的 tap_count | | | |
| 打字次数 | | | |
| 滚动次数 | | | |

> **判据（2026-10-01 补上 —— 这一节号称"唯一能直接验证核心假设"，之前却没有阈值）**：
>
> * **记录一组的 `tap_count` 差值 ≥ 2 次** 才算"明显更省事"（本品更少）；
> * **冷启动时间差 < 5 秒不算差异** —— 同一个人、同一台机器，5 秒内是噪声，
>   拿它当"更快"是自欺；
> * 两个条件**必须同时**满足才算这一节通过（写进 `docs/usability-test.md` 的通过判据）。
>
> 如果差值不是明显有利于本品，**核心假设就不成立**，不要用"用户不熟练"来解释——
> 用户对训记也未必熟练。

> **SUS-lite 那 4 题 2026-10-01 删掉了。** 原先 §7 给它留了一格时间，`tool/usability-report.mjs`
> 里也有目标值 `susLite: 80`，但**题项与计分公式全仓不存在**，而且脚本的判据是"没填就不判" ——
> 一个永远不生效的闸门。4 题简版的信度也撑不起"≥ 80"这条线。**删掉比补一套题更诚实**；
> 现在这一场唯一的最终裁判是下面的 Q3。

## 7. 现场流程（45 分钟）

| 时间 | 环节 |
|---|---|
| **开场前** | 装包 → **导入预置历史**（见下）→ 杀掉 App 冷启动一次 |
| 0–3 | 欢迎、知情同意、开录音 |
| 3–6 | 口播稿 + 器材确认（站起来、单手持机、拿水壶） |
| 6–12 | 冷启动（**全新安装状态**）→ T1，计时 + 计数 |
| 12–20 | T2 – T6 |
| 20–30 | 访谈提纲 6 题（逐字记录） |
| 30–38 | **对照环节**：用他自己的训记做同一件事 |
| 38–43 | Q3 关键选择（**整场唯一的最终裁判** —— SUS-lite 那 4 题 2026-10-01 删掉了，见 §6 末尾） |
| 43–45 | 付报酬、致谢、提醒不要对外透露内容 |

### 开场前必须做的一件事：导入预置历史

`usability/preset-6-weeks.json`（**生成的，不要手改**）让被试看到的不是一台空机：
首页有"上周练了 2 次"、建议卡有"上次 3 组 · 60kg×10"，**T6 的建议值真的就是 62.5kg**。

```bash
node tool/preset-history.mjs --write    # 跑测试当天重新生成（日期相对"今天"算，不刷新会过期）
node tool/preset-history.mjs --check    # 与生成器逐字节比对；放太久了它会提醒你重新生成
```

刷新 → 把文件内容发到测试机上 → 长按全选复制 →
「我 → 数据与备份 → 导入备份 → 从剪贴板粘贴」→ **杀掉 App 重开**。

> 这份数据不只是"随便造六周"：它被三条不变量钉着 —— **今天轮到胸**（所以最近一次训练是腿）、
> **真引擎对卧推算出 62.5kg**（3 组 × 10 次 @ 60kg ⇒ 加重 2.5）、
> **T4 的答案是 1800kg**（近 7 天卧推容量）。生成器自检和 `verify.sh` 都会核这三条。
> 细节与"为什么是 10 次不是 8 次"写在 `tool/preset-history.mjs` 的文件头。

## 8. 本场必须拿到的 7 个数字

收工时如果这 7 个数缺任何一个，这场测试就白做了。

| # | 数字 | 目标 |
|---|---|---|
| 1 | T1 完成率 | 5/5 |
| 2 | T1 中位耗时 | ≤ 90 秒 |
| 3 | **记录一组的中位 tap_count** | **= 1** |
| 4 | 首次训练全程打字次数 | 0 |
| 5 | 需滚动找动作次数 | 0 |
| 6 | T6 中"采纳建议 / 手改" | 记录，不看目标 |
| 7 | **Q3「明天去健身房带哪个 App」选本品的人数** | ≥ 3/5 |

**收工后不要手算**：

```bash
node tool/usability-report.mjs --template > usability/sessions/P1.json   # 每人一份
node tool/usability-report.mjs                                           # 7 个数字 + 通过/不通过
```

它会替你算中位数、对着上表逐条判，并在**分项加总 ≠ 合计 / 标了完成却没耗时 / 缺 T1**
这类抄错上直接报错 —— 手抄最容易出、又最不容易被发现的正是这几类。
输出的 markdown 块直接粘进 `docs/usability-test.md` 的「定量指标」一节。

## 9. 主持人常见错误（每次复盘对照）

1. **提示**："你试试长按那里" —— 一句话就毁掉一个数据点
2. **辩解**："这个是给专业用户设计的" —— 用户听到的是"你不够专业"
3. **诱导**："是不是比训记方便？" —— 直接污染最重要的结论
4. **问设计意见而不是问行为** —— 用户会给礼貌性好评，行为数据才是真的
5. **被试卡住时抢手机** —— 那一刻的表情和原话才是最值钱的信息
6. **让两个被试互相观摩** —— 第二个人会模仿第一个人的操作，两个数据点变一个
7. **测试前介绍产品** —— 用户会照着你的介绍去找功能，测的就成了你的讲解能力

# 极薄后端 · 设计（账号 / 增量同步 / 云备份）

> 状态：**设计稿，2026-09-30 起**。依据是两条已定决策：
> ①「双端先上」②「备份要账号」（见 `docs/tech-decisions.md` 的"服务端一期做到极薄"）。
> 实现前需要你确认第四节的三个子决策。

---

## 一、边界：只做三件事

`docs/tech-decisions.md` 已经定了服务端的形态，这份文档把它落成可实现的规格：

| 做 | 不做 |
|---|---|
| **账号**（匿名，见第三节） | 不做账号体系之外的用户画像/推荐 |
| **增量同步**（多端同一份数据） | **不做服务端计算**：规则引擎、渐进建议、PR 判定全在客户端 |
| **云备份**（换机恢复） | 不做实时协同（有真实"教练-学员"场景再说） |

**规则引擎留在客户端**不是技术偏好，是被场景逼的：健身房地下层没信号，
建议必须离线可算（这一点从一期就没变过，后端不能破坏它）。

## 二、为什么是现在

- 现在**换手机 = 靠用户自己导文件**。多数人不会做 —— 这是流失点，也是 `PRODUCT.md`
  自己写下的那条风险（"数据丢失是工具类死刑"）。
- 「备份要账号」的决策意味着：**这是第一个收费点**（比 AI 早，也比 AI 便宜）。
- 顺带解决一个卡了很久的行政问题：**App 备案的「APP 接入信息」**（现在没有服务器，
  填不了）—— 有了域名与服务器就能填了。

## 三、账号形态：匿名账号 + 恢复码（**不索取手机号**）

```
创建：App 生成随机 32 字节 → 作为账号密钥（account key）
      → 派生（HKDF）出两个东西：
          account_id  = 哈希(account key)   ← 发给服务端当账号标识（服务端只知道这个）
          recovery    = Base32(account key) ← 给用户抄下来（"恢复码"）
登录：输入恢复码 → 客户端算出 account_id → 服务端认得它 → 放行
```

- **不要手机号、不要邮箱**：与本产品"不索取可识别信息"的定位一致（也是隐私政策的卖点）。
- 恢复码丢失 = 账号找不回（服务端没有明文密钥，这是端到端加密的必然代价）。
  → 必须在界面上**把这件事说清楚**，并在开启备份时要求用户抄写 + 二次确认。
- 以后可选：允许把匿名账号"升级"绑定邮箱（用于找回），但**一期不做**。

## 四、端到端加密（服务端看不到训练与体重明细）

```
恢复码(account key)
  └─HKDF→ KEK（密钥加密密钥）
             └─ 加密 → DEK（数据密钥，随机 32B，存在服务端密文里）
                          └─ AES-256-GCM 加密每一个备份块
```

服务端存的只有：`account_id`（哈希）、密文块、每块的 `updated_at`/`bytes`/`nonce`。
**它看不到动作名、重量、体重、备注**。这样隐私政策只需披露"上传了加密后的备份"。

### 需要你确认的三个子决策

1. **加密实现**：用成熟包（`cryptography` 或 `pointycastle`）还是自己拼？
   → **我强烈建议用成熟包**。自己写密码学是这行最经典的自杀方式，而 pubspec 那条
   "依赖保持最小"的原则在这里要让位：**最小依赖 ≠ 连密码学都自己写**。
   （代价：多一个第三方依赖，要写进隐私政策与数据安全表。）
2. **恢复码的呈现方式**：一串 26 字符（Base32）抄写，还是配二维码（另一台设备扫）？
   → 建议**两者都给**：主推抄写（26 字符），二维码作为辅助。
3. **备份粒度**：只备份训练数据（记录/计划/身体数据），还是连设置一起？
   → 建议**全都要**（换机后设置也回来了），但**埋点 outbox 不备份**（那是本机的事）。

## 五、服务端数据模型（Postgres）

```sql
accounts(id text primary key,          -- = 客户端算出的 account_id（哈希）
         created_at bigint,
         deleted_at bigint null)

devices(id text primary key,           -- 设备标识（客户端生成）
        account_id text references accounts(id),
        name text, last_seen_at bigint)

backups(account_id text,               -- 一个账号一份"最新备份"（快照式，先不做版本树）
        blob bytea,                    -- 客户端加密后的整包（或分块的索引）
        bytes int, updated_at bigint,
        primary key (account_id))

sync_ops(account_id text, seq bigint,  -- 增量同步：客户端产生、服务端只追加
         op jsonb,                     -- {table, id, action, payload(密文), ts}
         primary key (account_id, seq))
```

**快照 + 增量两条路都要**：备份用于"换机一次拉全量"，增量用于"两台设备日常跟进"。
一期可以先只做**快照式备份**（增量同步留到真的有人两台设备时）——见第八节排期。

## 六、API 草案

| 方法 | 路径 | 做什么 |
|---|---|---|
| POST | `/v1/account` | 创建账号：客户端给出 `account_id`（哈希），服务端登记 |
| GET | `/v1/account/me` | 校验恢复码算出的 `account_id` 是否存在 |
| PUT | `/v1/backup` | 上传（覆盖）加密备份包 |
| GET | `/v1/backup` | 下载备份包 |
| DELETE | `/v1/account` | **注销并删除全部云端数据**（合规要求，必须有一键删除） |
| POST | `/v1/sync/ops` | 追加增量操作（可选，二期） |
| GET | `/v1/sync/ops?since=` | 拉取增量（可选，二期） |

鉴权：`Authorization: Bearer <account_id>`（因为 `account_id` 本身就是密钥的哈希，
不额外发明 token）。**因此必须走 HTTPS**，且服务端日志**不得记录 Authorization 头**。

阶段 1–3 **不依赖你买任何东西**（本地就能跑通并验证），阶段 4 开始才需要钱与账号。

   **我不擅自购买或注册**。

   建议的补救：默认关闭、开启时明确告知、端到端加密、服务端只有密文 —— 这三条都要
   写进商店描述与政策，别只写在代码注释里。

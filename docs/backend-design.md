## 一、边界：只做三件事

`docs/tech-decisions.md` 已经定了服务端的形态，这份文档把它落成可实现的规格：

| 做 | 不做 |
|---|---|
| **账号**（匿名，见第三节） | 不做账号体系之外的用户画像/推荐 |
| **增量同步**（多端同一份数据） | **不做服务端计算**：规则引擎、渐进建议、PR 判定全在客户端 |
| **云备份**（换机恢复） | 不做实时协同（有真实"教练-学员"场景再说） |

**规则引擎留在客户端**不是技术偏好，是被场景逼的：健身房地下层没信号，
建议必须离线可算（这一点从一期就没变过，后端不能破坏它）。

## 二、为什么是现在

- 现在**换手机 = 靠用户自己导文件**。多数人不会做 —— 这是流失点，也是 `PRODUCT.md`
  自己写下的那条风险（"数据丢失是工具类死刑"）。
- 「备份要账号」的决策意味着：**这是第一个收费点**（比 AI 早，也比 AI 便宜）。
- 顺带解决一个卡了很久的行政问题：**App 备案的「APP 接入信息」**（现在没有服务器，
  填不了）—— 有了域名与服务器就能填了。

## 三、账号形态：匿名账号 + 恢复码（**不索取手机号**）

```
创建：App 生成随机 16 字节 → 作为账号密钥（account key）
      → account_id = SHA-256(account key)        ← 发给服务端当账号标识（服务端只知道这个）
      → recovery   = Crockford-Base32(key) + 1 位校验 = 27 字符 ← 给用户抄下来（"恢复码"）
登录：输入恢复码 → 客户端算出 account_id → 服务端认得它 → 放行
```

- **不要手机号、不要邮箱**：与本产品"不索取可识别信息"的定位一致（也是隐私政策的卖点）。
- 恢复码丢失 = 账号找不回（服务端没有明文密钥，这是端到端加密的必然代价）。
  → 必须在界面上**把这件事说清楚**，并在开启备份时要求用户抄写 + 二次确认。
- 以后可选：允许把匿名账号"升级"绑定邮箱（用于找回），但**一期不做**。

> **落地时改掉了两处**（2026-09-30，见 `app/lib/backup/recovery_code.dart`）：
>
> 1. **32 字节 → 16 字节**。32 字节是 52 个 Base32 字符，没人抄得下来；
>    128 位随机早已超过穷举能力，**够用**。设计稿写 32 是没过脑子。
> 2. **Base32 → Crockford Base32 + 1 位校验**。字母表去掉 `I L O U`
>    （`0/O`、`1/I/L` 是手抄错误重灾区，解析时还把它们映射回去），
>    并加一位校验字符 —— **抄错一位要能当场发现**，而不是等到换机恢复时才发现，
>    那时用户已经找不到原件了。所以是 **27 字符**，不是 26。

## 四、端到端加密（服务端看不到训练与体重明细）

```
恢复码（16 字节 account key）
  └─HKDF-SHA256(info="lianleme/backup/v1")→ DEK（32 字节）
                                              └─ AES-256-GCM 加密整包备份
                                                 信封 {v,alg,kdf,nonce,ct,mac}
```

服务端存的只有：`account_id`（哈希）、密文信封、`bytes`/`updated_at`。
**它看不到动作名、重量、体重、备注**。这样隐私政策只需披露"上传了加密后的备份"。

> **落地时去掉了一层**：设计稿是 `KEK 包裹随机 DEK`（为了换密码时不必重加密）。
> 但我们的 `account_id = SHA-256(恢复码)` —— **换恢复码就等于换账号**，
> 旧备份本来就不该再用。包裹层换来的唯一好处在这里是伪需求，
> 而它要多存一个字段、多一层出错的可能。所以 DEK 直接由 HKDF 导出。
>
> **另外加了一条设计稿没写的：AAD 里绑 `版本 + account_id`**。
> 于是把 A 的备份挪给 B 用会直接认证失败 —— 服务端（或中间人）
> 拿一份**合法**密文也冒充不了另一份。这一条有对应测试。

## 五、服务端数据模型（Postgres）

```sql
accounts(id text primary key,          -- = 客户端算出的 account_id（哈希）
         created_at bigint,
         deleted_at bigint null)

devices(id text primary key,           -- 设备标识（客户端生成）
        account_id text references accounts(id),
        name text, last_seen_at bigint)

backups(account_id text,               -- 一个账号一份"最新备份"（快照式，先不做版本树）
        blob bytea,                    -- 客户端加密后的整包（或分块的索引）
        bytes int, updated_at bigint,
        primary key (account_id))

sync_ops(account_id text, seq bigint,  -- 增量同步：客户端产生、服务端只追加
         op jsonb,                     -- {table, id, action, payload(密文), ts}
         primary key (account_id, seq))
```

**快照 + 增量两条路都要**：备份用于"换机一次拉全量"，增量用于"两台设备日常跟进"。
一期可以先只做**快照式备份**（增量同步留到真的有人两台设备时）——见第八节排期。

## 六、API 草案

| 方法 | 路径 | 做什么 |
|---|---|---|
| POST | `/v1/account` | 创建账号：客户端给出 `account_id`（哈希），服务端登记 |
| GET | `/v1/account/me` | 校验恢复码算出的 `account_id` 是否存在 |
| PUT | `/v1/backup` | 上传（覆盖）加密备份包 |
| GET | `/v1/backup` | 下载备份包 |
| DELETE | `/v1/account` | **注销并删除全部云端数据**（合规要求，必须有一键删除） |
| POST | `/v1/sync/ops` | 追加增量操作（可选，二期） |
| GET | `/v1/sync/ops?since=` | 拉取增量（可选，二期） |

鉴权：`Authorization: Bearer <account_id>`（因为 `account_id` 本身就是密钥的哈希，
不额外发明 token）。**因此必须走 HTTPS**，且服务端日志**不得记录 Authorization 头**。

## 七之五、阶段 1 实况（2026-09-30 完成）

`server/backend.mjs`（零依赖 HTTP）+ `server/backend-store.mjs`（`node:sqlite`）+ 
`server/backend.selftest.mjs`（17 条断言，已进 `verify.sh` 第 2 层）。

**与设计稿的两处偏离，都是刻意的**：

1. **存储先用 `node:sqlite` 而不是 Postgres** —— 为了零依赖、本地就能跑通并自检。
   接口按可替换写（`createSqliteStore` 的那几个方法），换 Postgres 只改这一个文件。
   ⚠️ Node 22 的 `node:sqlite` 会打印 ExperimentalWarning，上线前若换 Postgres 一并处理。
2. **一期只做快照式备份，不做增量同步** —— 增量留到真的有人两台设备时（设计稿第五节已说明）。

自检里盯住的四件事：接口真的通（真 HTTP 往返）、**上传什么字节就下载什么字节**
（服务端不解析不改写）、**注销是真删**（库里也不留）、以及三条隐私承诺
（元信息接口不含备份内容 / 日志不漏 `Authorization` / 不记录 IP）。

**自检抓到的两个自己的错**（都留了注释）：
* 超限时第一版直接 `req.destroy()` —— 客户端拿到的是"socket 被对端关闭"而不是干净的 413。
  掐断连接不是拒绝请求的正确姿势；改成读完但不再缓存，再正常回 413。
* 自检里用猴子补丁 `console.log` 抓服务端日志，**把自检自己的输出也吞了**
  （只看得到最后一行）。改成给 `createBackend` 注入 `log` —— 比补丁干净，也更好测。

## 七之六、阶段 2 实况（2026-09-30 起，客户端加密层已完成）

阶段 2 拆成两半做，先做**看不见但最要紧的那半**：密钥与账号。
界面（备份/恢复屏）与隐私政策同步放在后半段 —— 它们依赖这一层的形状定下来。

| 文件 | 干什么 |
|---|---|
| `app/lib/backup/recovery_code.dart` | Crockford Base32（去掉易混的 `I L O U`）+ 1 位校验；16 字节 → 27 位；`O→0`、`I/L→1` 归一化 |
| `app/lib/backup/backup_crypto.dart` | HKDF-SHA256 导出 DEK → AES-256-GCM 信封 `{v,alg,kdf,nonce,ct,mac}` |
| `app/lib/backup/backup_transport.dart` | `BackupTransport` 抽象 + `HttpBackupTransport`（只用 `dart:io`）+ 测试用假传输 |
| `app/lib/backup/cloud_backup.dart` | 把三块拼起来：建号 / 登记 / 上传 / 找回 / 注销 |

**四个刻意决定**：

1. **没有"被包裹的 DEK"**。常见做法是 KEK 包一个随机 DEK，好让换密码时不必重加密。
   但我们的 `account_id = SHA-256(恢复码)`：换恢复码就等于换账号，旧备份本来就不该再用
   —— 包裹层换来的唯一好处在这里是伪需求，而它要多存一个字段、多一层出错可能。
2. **AAD 里绑了 `版本 + account_id`**。于是把 A 的备份挪给 B 用会直接认证失败：
   服务端（或中间人）拿一份**合法**密文也冒充不了另一份。
3. **恢复码先本地校验，再碰网络**。抄错一位的用户不该先等一次网络往返、再看到一句
   "服务器返回 401"。测试里直接断言"抄错一位 → 网络调用数为 0"，
   这条同时也是**误删别人账号**的护栏。
4. **传输层会抛异常，而不是返回 false** —— 和埋点传输层恰好相反。埋点送不出去必须静默
   （绝不能影响功能），备份送不出去必须让用户看见（他以为数据已经安全了，其实没有）。
   做成返回值早晚有人忘记看。

### "服务端看不到明细"是怎么被证明的

`app/test/cloud_backup_test.dart` 后半段**真的把 `server/backend.mjs` 拉起来**
（`--port 0`，端口从 stdout 解析），用真实 HTTP 走完建号 → 上传 → 找回 → 注销，
然后**直接读那个 sqlite 文件的字节**，搜明文记号（`MARKER-…` / `深蹲` / `102.5` / `weight_kg`）。

⚠️ "搜不到明文"这种断言**天生可能是空的**（万一备份压根没落盘）。
所以测试里先做**阳性对照**：先确认密文那一长串 base64 确实躺在文件里，
再确认明文一个片段都不在。少了这一步，这条测试就是在自我欺骗。

**2026-09-30 补：真机端到端之后，宿主端那次"手工核 sqlite"已经固化成命令了** ——
当时是一次性动作（查完就没了），下一个人没法原样重跑：

```bash
node tool/check-ciphertext.mjs /tmp/e2e/backend.sqlite      # 核服务端那份库
node tool/check-ciphertext.mjs <库> --absent 深蹲,102.5      # 追加你要找的明文记号
node tool/check-ciphertext.mjs --selftest                  # 自检（verify.sh 第 2 层每次跑）
```

**回复之后"数据真的回来了"也是逐字段验的**（2026-09-30 加强）：这条端到端原来只验到
"统计卡显示 2 组" —— **个数对不等于内容对**（恢复出来的重量/次数/动作错了，那一步照样绿）。
现在流程改成：记完两组先**读本机真实库抄一份快照**（id / workoutId / 动作 / 组序 / 次数 /
重量 / 完成时间 / 组类型），恢复之后再读一次，`orderedEquals` 比对。
最近一次的结果（日志原样）：

```
snapshot-before=s_w_…_ex_bb_bench_press_1|w_…|ex_bb_bench_press|1|8|40.0|1790761768665|normal ／ …_2|…|2|8|40.0|…|normal
snapshot-after =（与上面逐字节相同）
verified-2-sets-restored (field-by-field) · E2E-OK
```

连**完成时间戳**都原样回来了 —— 这一点值得单独说：如果恢复时把时间重写成"现在"，
进步曲线与"上周练了几次"就会错，而只数条数的断言看不出来。

它查四件事：`backups` 里**至少有一行**（空库不算"安全"，算"还没跑"）、
信封结构是 `{v, alg, kdf, nonce, ct, mac}` 且 `alg` 是 AES-256-GCM、
`ct` 解出来**不像 JSON**且可打印率低、整包搜不到任何明文记号。
`--selftest` 会**故意造一份"ct 其实是明文"的库**，要求工具报错 ——
少了这一步，这条检查可能只是"永远打印 ✓"的假守卫（已接进门禁第 2 层）。

**踩到的两个坑**（都留了注释）：

* 服务端 `--port 0` 时原来打印的是 `0`，自动化测试拿到就没法连 —— 改成打印
  `server.address().port` 的真实端口。
* Dart 侧 `stdout.firstWhere(...)` 拿到第一行后**会取消管道订阅**，node 下次往 stdout
  写东西就收到 EPIPE、**整个进程直接死掉**。症状极具误导性：第一个请求
  "Connection reset by peer"，之后全部 "Connection refused"，看起来像服务端有 bug。
  改成广播流 + 一个永不取消的订阅把管道一直抽干（stderr 同理）。

### 两处"看起来可以更好、但我们有意先这样"的地方

**① 恢复码是明文存在 App 私有数据库里的**（`backup_account.recovery_code`）。
它是账号的唯一凭据，所以"该不该塞进 Keychain / Keystore"值得说清楚：

* 威胁模型上它不是最弱的一环 —— **同一个库里就是全部训练记录**。能读到这个库的人
  已经拿到了数据本身，恢复码只是再多给他一份"云上那份"的访问权（而那份本来就是同一批数据）。
* 用系统钥匙串要多一个插件（`flutter_secure_storage` 之类）→ 新的依赖、新的 iOS/安卓差异、
  隐私政策与事实表又要跟着改。**一期为这一条引入原生依赖不划算。**
* 真要加固，正确的顺序是"先加密整个本地库"，而不是单独把这一列搬走。

**② 备份里带了一份"动作名表"，所以 2 组也有 22 KB**（阶段 5 实测数）。
`encodeBackup` 会把**动作 id → 中文名**的映射一起写进去（从库里取全量：351 个动作约 10 KB）。

⚠️ **2026-09-30 核对：这份映射是「只写不读」的，所以当初写的那个好处并没有兑现。**
原文这里写着「这样**恢复时即使动作库变了也能显示中文名**」——但 `parseBackup` 根本不读
`exercise_names`，导入时也不会把缺失的动作补进本机库。实际后果（已有测试钉着，
`app/test/backup_scope_test.dart` 的那条"导入时不读它"）：

* 在一台没有该动作的手机上导入备份 → **记录不会丢**，但这个动作在界面上显示成
  **id 本身**（`ex_xxxxxxxx`），而不是备份里那个中文名 —— 因为界面取名字的写法是
  `names[id] ?? id`（progress / training_stats / CSV 三处都是这个兜底）；
* 于是这约 10 KB **目前是纯开销**：付了成本、没拿到承诺的好处（2 组 22 KB 里它占一半）。

**两条路，二选一**（都进 `docs/your-todo.md` 了）：
(a) **把映射用起来** —— 导入时若本机缺这个动作，就用它建一个（标成自定义动作）；
(b) **或者把映射去掉** —— 备份体积立刻小一半，代价是"跨版本/跨库恢复"时动作名只剩 id。
一期的建议是 **(a)**：它本来就是设计意图，而且"导回来是同一批数据"这句对用户更值钱。

## 七之七、阶段 5 实况：真机端到端（2026-09-30，在**模拟器**上完成）

设计稿里阶段 5 写的是"备份 → 卸载重装 → 恢复 → 数据一致"。这一条**已经跑通了**，
而且**全程只用 App 自己的界面**（不是拿 Dart 脚本冒充）：

| 步 | 做了什么 | 现场证据（`LIANLEME-E2E` 日志） |
|---|---|---|
| 1 | 真实 App 里记两组 | `logged-2-sets` |
| 2 | 我 → 云备份 → 开启（**真后端建号**） | `account-created code=XC5NE-SGYPG-DSA7G-E6CYX-SJ5PB-0M` |
| 3 | 立即备份 | `uploaded: 已备份 1 次训练 / 2 组（22.0 KB 密文）` |
| 4 | 界面显示**服务端**那份的状态 | `server-state: 云端：22.0 KB · 09-30 13:33` |
| 5 | **删除全部数据**（故意**不勾**"同时删除云端备份"）← 等于换了台新手机 | `local-data-deleted (cloud kept)`；本机回到空态 |
| 6 | 用那串恢复码"取回已有备份" → 从云端恢复 | `adopted-existing-code` / `restored: 已从云端恢复：已导入 1 次训练 / 2 组` |
| 7 | 断言数据真的回来了 | `verified-2-sets-restored`（「我」页总组数 = 2 组） |

**宿主侧同时核了服务端手里到底是什么**（同一时刻读它的 sqlite）：

```
accounts: 1 条        backups: 1 条   bytes=22567（与设备报的 22.0 KB 一致）
blob 开头: {"v":1,"alg":"AES-256-GCM","kdf":"HKDF-SHA256","nonce":"8t/R…
```

* **阳性对照**（必须先成立，否则下面的"搜不到"是空转）：
  `AES-256-GCM` / `HKDF-SHA256` / `{"v":1` 在**库文件字节**里都能搜到 → 密文确实躺在那里。
* **阴性**：`ex_bb_bench_press` / `weight_kg` / `"reps"` / `40.0` 在**整个库文件**里都搜不到。

也就是说："**服务端看不到训练明细**"这句话，现在有成对的证据（设备侧断言 + 宿主侧翻库），
而且用的是**真机产生的载荷**，不是测试里构造的那一份。

**怎么复现**（测试与 driver 已入库）：

```bash
node server/backend.mjs --port 8790 --db /tmp/e2e/backend.sqlite &
adb -s <设备> reverse tcp:8790 tcp:8790          # 必须走回环，见下
adb -s <设备> shell pm clear com.sdknwdtvpv.lianleme
cd app && flutter drive --driver=test_driver/cloud_e2e_driver.dart \
    --target=integration_test/cloud_backup_e2e_test.dart -d <设备> \
    --dart-define=LIANLEME_BACKUP_URL=http://127.0.0.1:8790 \
    --dart-define=LIANLEME_BACKUP_DISCLOSED=true      # 少了这个，入口不出现（失败往关闭倒）
```

> 为什么是**两个**开关：地址一旦配上，界面就会出现云备份入口，而政策正文是按「是否启用」写的（没启用时必须写「本版本未提供云备份」）—— 只给地址会做出一个**界面与政策自相矛盾**的包。所以少了声明开关就当作**没配**：入口不出现、一个字节都不发。`tool/privacy-audit.mjs` 会检查「教人开云备份」的地方有没有同时写这两个开关。

> ⚠️ **不能用模拟器那套 `10.0.2.2`**：`dart:io` 会拒绝明文 HTTP 发往非回环地址
> （"Insecure HTTP is not allowed by platform"），而**回环有豁免** ——
> 所以一律用 `adb reverse` + `127.0.0.1`。生产永远走 https，这条只影响本地验证。

**当时的设备**：Android **模拟器**（Pixel 6 / API 36 / arm64，无头）。
**真机（Redmi `flourite`）仍然锁着**，所以"真机"这两个字在本文里要看得仔细：
链路、加密、服务端行为都由这次跑通；**真机特有的**（Doze、厂商后台策略、真实网络切换）
还没有验过 —— 那需要解锁真机。

### 阶段 4 的落地包（`server/deploy/`，2026-09-30 备好）

买好服务器之后，部署**不需要现场设计** —— 这一包把该定的都定死了：

| 文件 | 干什么 |
|---|---|
| `install.sh` | 幂等安装：查 Node ≥ 22.5 → 建不可登录的系统用户 → 建目录 → 拷 3 个服务端文件 → 渲染并装两个 systemd 单元 → 装 Caddy 与反代 → **自己 curl 一次 /healthz** 再报成功。`--dry-run` 可以先看它要做什么（不需要 root） |
| `lianleme-backend.service` / `lianleme-collector.service` | 开机自启、崩了重启；`ProtectSystem=strict` + `ReadWritePaths=<数据目录>` + `CapabilityBoundingSet=`，**只监听 127.0.0.1** |
| `Caddyfile` | 一个域名对外：`/v1/events` → 收集端、其余 `/v1/*` → 备份服务；TLS 自动申请。⚠️ **故意没有 `log` 指令** —— 政策写着"不做 IP 记录"，而 access log 会记客户端 IP |
| `README.md` | 你要给我哪三样（IP/SSH、域名、备案状态）、装完怎么验、客户端要编哪两个 `--dart-define` |

`tool/check-deploy.mjs`（门禁第 2 层，带 10 例自检）盯住这一包的内部一致性：
端口在 install.sh ↔ 单元 ↔ Caddyfile 三处必须一致、`ExecStart` 指的入口真的存在、
模板里的占位符 install.sh 全都替换、**与 `app/lib` 里两个 `String.fromEnvironment`
的字面量逐字相同**（不然照 README 编出来的包会静默关掉云备份）、加固项没被删、
Caddyfile 没开访问日志。

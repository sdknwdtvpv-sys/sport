## 全局规范

- **5 个 Tab**：训练 / 进步 / 数据 / 计划 / 我的 —— **2026-10-05 已落地**（v1.45.0，`app/lib/core/app_tab_bar.dart`）。

⚠️ **两条与旧版不同、且是刻意的**（2026-10-05 按用户拍板的新 VI 改）：
  * 首页从"标题贴顶 + Spacer + 按钮压底"改成**可滚动信息流**：四块内容塞不进原来那套布局，

  * 快速入口与 VI 不同（VI 是"自由训练/动作库/训练计划/成就"）：**计划已是一级 Tab、成就还没做**，

**规则**：无注册、无引导页、无授权请求。

> **底部 Tab 栏**（2026-10-06 第二轮改）：iOS 上它**浮在内容之上**（不是排在内容下面），
> 所以滚动时真实内容从玻璃背后经过 —— 那正是它好看的原因，**不再自己垫任何渐变**。
> 材质是 **iOS 26+ 的原生液态玻璃**（`UIGlassEffect` `.regular`）：**底托 + 选中那一格的
> 胶囊是两块各自独立的玻璃**，选中的胶囊往里缩 5pt、带一点白（这是"选的是它"唯一的提示，
> 苹果也是这么做的）；**iOS 26 以下退回系统材质**；
> **Android 与以前一个像素都不差**（`GlassSurface` 在非 iOS 上原样返回）。
> 于是内容区底部要留出 `AppTabBar.reservedSpaceFor(context)`（否则最后一项被压在玻璃下面）。
> **iOS 上还可以左右拖着换 tab**（`PageView`），拖的时候那颗玻璃**跟着手指滑**；
> Android 仍然是"直接换一屏"（同一个平台判据）。
> ⚠️ 真机 release 的帧率还没测（platform view 有整屏合成代价）—— 这一条记在
> `feature-backlog.md` §〇「⑦」里，别当成已验。

**中间那块摆「今天的安排」**（2026-10-04 加，真机投诉"标题与按钮之间空太大"）：
原来那里是一个 `Spacer()`（2026-10-01 为了把按钮压进拇指区改的，**那个目标是对的**），
代价是越高的手机中间越空 —— 现在换成用户此刻最想知道的东西：**今天练什么、每个动作做多重**。
三条纪律：**点它不开练**（开练永远是大按钮的事；整块点进 S2 建议卡，卡内只有「换一批」是
另一个目标）；**与大按钮同一份计划**（`main.dart` 持有 `_todayPlan`，显示了 A 却练 B 比不显示更糟）；
**按钮位置不动**。计划为空时卡片**照常显示**（"今天还没有排动作 / 点这里看看怎么练"）——
`_loadTodayPlan()` 是吞异常的，卡片一消失，只在 S2 里的「我自己选 / 我的计划」就够不着了。
⚠️ 加卡片之后矮屏会溢出，所以整屏改成"填满视口、内容更高时可滚动"（`IntrinsicHeight` 那一招）。

**主按钮一跳直开练**（2026-09-29 改）：点一下**直接进 S4**，用今天的第一条建议，
不再强制经过 S2。原因是端到端口径下"今日页 → 建议卡 → 大按钮"= 3 次点击才记下第一组，
而 `PRODUCT.md` §1 的红线正是"超过 3 次点击判负"——刚好压线。
现在第一组 **2 次**，同一动作的第 2 组起 **1 次**。

**S2 没有被砍掉**，只是不再单独占一行（2026-10-04，v1.40.0）：原先那行「看看今天练什么 ›」
删掉了，改由**「今天的安排」卡整块**承担 —— 卡已经把"今天练什么"回答了，同一件事不留两个入口；
而「我自己选 / 我的计划」**只在 S2 里**，所以入口不删、只换成更大的触摸目标。
理由与证据见 `CHANGELOG.md` v1.40.0 与 `docs/product-review-2026-10-01.md` ➖2。

**S13 入口**（「不知道怎么练？帮我定个计划 ›」）只在还没定过计划时显示。

## S2 · 今日建议卡

```
┌─────────────────────┐
│ 今天练 胸 + 三头  ⟳ │
├─────────────────────┤
│ 卧推       62.5kg×8 │
│ 上次 3 组全部达标，  │
│ 线性加重 +2.5kg      │
│ 上次 3 组 · 60kg×10  │
├─────────────────────┤
│ 上斜哑铃卧推 22kg×8 │
│ 绳索下压    25kg×10 │
├─────────────────────┤
│ ┌─────────────────┐ │
│ │   开始训练       │ │
│ └─────────────────┘ │
│  换一批   我自己选    │
└─────────────────────┘
```

**每条建议必须显示理由。** 理由放不下 = 建议不合法。

**理由下面还要有"证据"**（2026-09-29 加）：把引擎据以判断的**事实**原样摆出来 ——
「上次 3 组 · 60 kg × 10 次」。理由回答"为什么是这个数"，证据回答"你凭什么这么说"。

这是"计划与历史实时闭环"这个卖点在界面上**唯一可见的地方**，也是它可被反驳的地方：
用户看到"这不是我上次记的"，那本身就是有用的反馈信号。次数在组间不一致时只报**最少**的
那一组 —— 那正是引擎做判断的口径。第一次练这个动作时没有这一行（理由文案已经说了）。

> **实现时的一处偏离**：规格里「换一批」在标题栏（⟳）和底部各有一个入口。
> 实现只保留底部一个 —— 同一个动作在一屏出现两次，是极简产品最该避免的冗余。
> 真源见 `app/lib/features/today/today_suggestion_screen.dart` 的文件头注释。

**列表里的动作说明**：写过的动作会在副标题接一句要点（「胸 · 杠铃 · 肩胛后收贴凳…」）——
351 个动作里目前推荐位全覆盖、长尾部分空白（`tool/content-report.mjs` 可查覆盖率与队列）。
没有说明的动作不会显示空的一行。

**三行筛选 chip**：部位（胸/背/腿/肩/手臂/核心）+ 器械（杠铃/哑铃/器械/绳索/自重/弹力带/壶铃）
+ 类型（全部类型/热身/有氧/拉伸）。

* **器械那一行**（2026-09-29 加）是给**家里只有一对哑铃、或只有自重**的人用的 ——
  以前 `search()` 不支持按器械过滤，居家用户会被推荐杠铃卧推和腿举。
* **类型那一行**（2026-09-29 加）是给热身、有氧与拉伸的。它们和力量动作的使用时机不一样
  （练前/练后/单独做），混进 342 条里按常用度排在最末等于没有入口。
  `strength` 不单独给 chip —— 它是这个 App 的默认语境，"全部类型"减去热身与拉伸就是它。
  列表里这三类的动作会在副标题上标出类别（「拉伸 · 腿」），免得用户不知道筛了什么。

三行都可以与搜索叠加；筛过之后列表回到平铺态（分区是"还不知道练什么"时的陈列，筛完就说明已经知道了）。

## S3 · 动作选择器

- 搜索框（支持别名："bp" → 卧推）
- 四个分区：**置顶**（2026-10-04 加）/ 最近做过 / 常用 / 按部位筛选
- 每行右侧一个**置顶星标**（`Key('pin-<动作id>')`）—— 点一下钉住/取消
- 右上角「新建自定义动作」
- 目标：从打开到选中一个动作 ≤ 5 秒，不滚动

**「置顶」是唯一一处"用户直接表态"的分区**：另外三个都是系统猜的
（最近做过 = 时间，常用 = popularity，部位 = 分类）。
所以它排在最前、且置顶的动作**从其它分区里去重**（同一屏出现两次只会让人多滚一次）。
顺序就是用户钉的顺序（落 `pinned_exercise.position`，不靠毫秒）。
⚠️ 置顶的动作被删（自定义动作可以删）→ **静默跳过**，不显示一行点不动的动作。

## S4 · 训练中主屏 ★核心屏

```
┌─────────────────────┐
│ ← 卧推        1/3 组 │
│                     │
│   上次 60kg × 8      │
│                     │
│   第 1 组            │
│                     │
│ ┌─────────────────┐ │
│ │                 │ │
│ │   60kg × 8  ✓   │ │
│ │                 │ │
│ └─────────────────┘ │
│                     │
│  ○ 60×8 ✓           │
│  ○ 60×8 ✓           │
├─────────────────────┤
│ 休息 01:12 −15 +15 跳过│
├─────────────────────┤
│ ‹ 绳索下压   上斜推 ›│
└─────────────────────┘
```

**铁律**：
- 屏幕中央**只有一个**主按钮，按钮上就是将要写入的值
- **1 次点击 = 1 组**，这是全产品唯一不可妥协的指标
- 组列表只显示已完成的，未完成的不占位（避免"计划感"压迫）
- 休息倒计时自动开始，可跳过，可关闭

**v1.53 在真机上补的四处**（用户带着 v1.52.0 去健身房练了一次之后提的）：

| 加了什么 | 为什么 | 判据 |
|---|---|---|
| 标题栏右边「换动作」 | 健身房最高频的意外是**器械被占**：原来只能退出训练重选，重量次数还得重填 | 换的是当前那一格；新动作的重量来自**它自己的历史**；已记的组一条不动；同部位预筛 |
| 大按钮上方「上次 N 组 · 45 kg × 10 次」 | 站在器械前最想知道的数字，原先只藏在建议页那条证据链里 | 没有历史就**不出现**（不编） |
| 休息条的 **−15 / +15** | 「今天想多歇半分钟」几乎必然发生，而原先只有「跳过」 | 改的是**结束时刻**（与锁屏倒计时同一份真相）；不计入 `tap_count` |
| 计时动作的**做组计时器** | 平板支撑原来要在垫子上自己数 | 弹层「开始计时」→ 大按钮变成在走的秒数 → 点一下记下；到今天的秒数震两下 |

另外两处"体外"的改动：**训练屏期间屏幕常亮**（离开就恢复，不全局常亮）；
**Android 上休息结束发一条本地通知**（iOS 有 Live Activity，不需要）。

**单位由动作类型决定**（`track_type`，见 `docs/data-model.md`）：按时长动作
（平板支撑 / 侧平板）那个数字是**秒**，大按钮与组列表都写「自重 × 30 秒」——
不写单位会被读成「30 次」。同一套界面，不为其单独开屏。

**撤销**：长按「已完成」里的任意一行 500ms，撤销那一组（本地软删除 + 进同步队列 +
上报 `set_undone`）。撤销后大按钮上的值不动，手抖点快了可以再点一下补回来。
为什么不是右滑，见 `docs/interaction-spec.md` §7。

## 单位：训练重量与体重分开，开关的位置也不一样（2026-09-29）

| 单位 | 选项 | 开关在哪 | 影响 |
|---|---|---|---|
| 训练重量 | kg / lb | **「我 → 偏好设置 → 显示」**（弱化成一行） | 杠铃、哑铃、容量、PR 的念法 |
| 体重 | kg / lb / 斤 | **S12「身体数据」页，就在「体重」标签那一行的右边** | S12 录入框、S12 列表、S8 体重卡片的念法 |

**为什么分开**：中国用户称体重还爱说斤（1 斤 = 500 g），而杠铃重量说 kg。
一个开关管两件事就会打架 —— 训练重量与体重的取值集合不完全一样
（训练重量没人说"两百斤"，体重又常按斤记）。

⚠️ **2026-10-01 修了一处真实的不一致**：体重那边原先只有 kg/斤，于是
**全局选了磅的用户打开身体数据页看到的还是 kg** —— 两套口径各说各的（真机走查拍到的）。
现在两边取值集合一致（kg / lb / 斤），并且**默认联动**：全局换单位时，体重单位
只要还处于"跟着全局"的状态就一起换；用户单独选过（比如「斤」）则保持不动
（判据在 `ProfileRepository.setUnit`）。

**为什么开关的位置不同**（v1.7.0 按用户反馈改的）：单位是"设置一次就不管"的东西，
不该占着设置页第一屏；而**称体重的时候**才想起来"我要按斤看"，所以体重的开关

**两处必须一致**：S12（录入与列表）与 S8（体重卡片）用的是**同一个**体重单位。

### S1 首页 2026-10-01 的两处变化

* **「继续上次的训练」条**（有未结束的会话时才出现）：摆在主按钮**之前** ——

### S7 总结页：多了一行「下一次」

练完那一刻是**唯一一个用户愿意想"下一次"的时刻**（回到首页注意力就散了）。
总结页现在会显示「下次轮到 X（今天练的是 Y）」，部位轮转用的是 planner 的同一套规则，
所以它与首页、建议卡的口径一致 —— 不会两处说两样话。

**「数据与备份」里有三个出口，别混**：

| 入口 | 是什么 | 能不能导回来 |
|---|---|---|
| 导出全部记录 | CSV 到剪贴板 —— **给人看的报表**（日期/动作/重量/次数/容量/组序） | ❌ 不能：日期只到分钟、重量跟显示单位走 |
| **导出备份文件** | JSON，交给系统分享面板（存「文件」/发给自己） | ✅ 能：重量一律 kg，组 id、训练 id、热身标记、RPE、秒级时间都在；**身体数据与身高也在**（2026-10-05 起，且只在你仍持有那道单独同意时） |
| **导入备份** | 把备份内容粘进来（长按输入框粘，或点「从剪贴板粘贴」） | —— 幂等：同一份粘两次不会变成两份 |

导入这条路径同时解决三件事：数据可携带（PIPL）、换手机能回来、
以及可用性测试要的"预置 6 周历史"（`docs/usability-test.md` §2）。
错误**留在弹层里**显示 —— 关掉弹层再弹 SnackBar，用户就得重新粘一遍。

**第四个出口：云备份**（v1.21.0，`app/lib/features/backup/cloud_backup_screen.dart`）。
它和上面三条的关系要先说清楚，否则很容易被当成"又一个备份按钮"：

* **入口可能根本不存在**。云备份需要一台服务器，地址是**编译期**配的
  （`--dart-define=LIANLEME_BACKUP_URL` ＋ `--dart-define=LIANLEME_BACKUP_DISCLOSED=true`，两个都给才作数）。没配的包里「数据与备份」页连这一行都不显示 ——
  一个点进去必然报错的入口，比没有这个功能更伤（见 `lib/backup/backup_config.dart`）。
* **默认关闭**，开启要过两道：先说清**"这一份里到底有什么"**
  （训练记录 / 动作置顶 / 身体数据，2026-10-05 起逐项写明）＋"服务端只拿到密文 /
  恢复码丢了找不回"，再展示恢复码并要求勾上"我抄在纸上了"。**恢复码只显示这一次。**
  这份清单与政策 §3.3 是同一份，改一处要改两处。
* **"关闭"与"注销"是两件事**，按钮和文案都分开：关闭只清本机凭据（云端那份还能用恢复码
  取回），注销才连云端一起删。
* 从云端恢复是**合并**（组与训练按 id upsert），不覆盖本机 ——
  与「导入备份」共用同一份实现（`features/profile/backup_source.dart`），免得两条路长歪。
  **身体数据同理，而且只增不减**：恢复只会补上或覆盖"同一天"那一条，
  绝不删掉你在新手机上自己记的（`backup_scope_test.dart` 钉着）。
  ⚠️ 新手机上**还没过**「身体数据」那道单独同意时，备份里带的那些**一条都不会写进去**，
  摘要里会如实说"另有 N 条没进来（先去「身体数据」页同意，再恢复一次）" ——
  这是那道单独同意门的必然结果，不是缺陷。

| --- | --- | --- |

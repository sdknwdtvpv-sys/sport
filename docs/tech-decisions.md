## 客户端：Flutter + 原生 Swift 扩展

| 选择 | 理由 |
|---|---|
| **Flutter 而非 RN** | 一套渲染管线，双端像素级一致。`less is more` 的设计经不起两端体验漂移，也不该维护两套 UI 分支。60fps 列表与自绘图表完全可控 |
| **本地优先：drift (SQLite)** | 响应式查询 + schema 迁移成熟，训练中零网络依赖（见 `data-model.md` 的同步设计） |
| **Apple Watch 用原生 Swift 扩展** | **手表独立 App 双端框架无解，必须原生**。MVP 不做手表独立 App，**也不接 HealthKit** —— 2026-09-30 拍板推到**后续版本**（它是敏感健康数据，要走单独同意 + 政策 + 授权说明 + 审核 5.1.3，是一条独立工作流） |
| **Android 侧** | 同理，**Health Connect 也推到后续版本**（与 iOS 同一版节奏，不同步做半套） |

> **备选 RN 也完全成立** —— 训记本身就是 RN（包名 `com.trainnote.rn`），在该场景已被验证。若团队是 JS 背景，选 RN 的成本远低于切 Flutter。**这条取决于团队的人，不取决于技术优劣。**

**为什么"双端"反而强化了 Flutter 的理由**：单端时你可以为 iOS 做精细打磨、Android 稍差也能接受；双端同步上线意味着两端的体验差距会直接暴露，而本产品的核心资产恰恰是"一致的省事感"。

## 已知警告（Xcode 里那个"1 issue"，2026-09-30 记）

在 Xcode 里打开本工程时，issue 列表里会看到 **1 条警告**，挂在 `FPPSharePlusPlugin` 节点下
（**不在 `Runner` 自己的源码里**）：

```
'keyWindow' is deprecated: first deprecated in iOS 13.0
  → share_plus 的 ios/share_plus/Sources/share_plus/FPPSharePlusPlugin.m:25
```

**它是什么、为什么不用管**（查证过的三条）：

1. **插件本来就写对了**：`RootViewController()` 先 `if (@available(iOS 13, *))` 走
   `connectedScenes → UIWindowScene.windows → window.isKeyWindow`；被标黄的那行是 **`else` 分支**，
   也就是 **iOS < 13 的回退路径**。
2. **它在我们的部署目标上永远执行不到**：`IPHONEOS_DEPLOYMENT_TARGET = 15.0`
   （`app/ios/Runner.xcodeproj/project.pbxproj` 里三处都是）。Xcode 标黄是**编译期**的弃用检查 ——
   哪怕写在 `@available` 守卫里也照样标，**不是运行时问题**。
3. **没有"升级就能消掉"这条路**：我们锁的 `share_plus 13.3.0` 已经是最新
   （`flutter pub outdated`：direct dependencies all up-to-date）。

**怎么自己确认**（三条，都不需要信我）：

```bash
grep -rn "keyWindow" ~/.pub-cache/hosted/pub.dev/share_plus-13.3.0/ios/   # 看那段 @available 分支
grep -n "IPHONEOS_DEPLOYMENT_TARGET" app/ios/Runner.xcodeproj/project.pbxproj
cd app && flutter pub outdated | grep -i share_plus                        # 是否已有新版
```

**边界（免得被当成"iOS 侧全都验过了"）**：这条警告与**分享面板本身没有自动化**是两件事 ——
`share_plus` 拉起的是**系统 UI**，`integration_test` 点不到它（`docs/release-admin.md`
的差异清单里第 3 条已写明，只有"存相册"那条路是自动验过的，两条权限路各走一遍）。

> 想彻底清掉它只有**上游修**（给那一行加 `#pragma clang diagnostic ignored "-Wdeprecated-declarations"`，
> 或删掉 iOS < 13 分支）。本地 patch 依赖**不建议**：pub-cache 是共享的，
> `pub upgrade` 或换机器就没了 —— 而且改依赖的风险远大于这一条警告。

## 为什么还要一层"场景级 eval"（2026-09-29 定）

**问题**：`engine/vectors.json` 的向量管的是**单步正确性** —— 给一个输入，输出对不对。
但用户感受到的不是单步，是"**连练 12 周之后，这个 App 说的话还讲不讲道理**"。
每一步都正确的函数，串起来照样可能走成荒谬的轨迹（这正是分析报告里那句
"209 项测试全绿，而核心引擎从未在真实路径上运行过"的同类问题，只是换了层次）。

**做法**：`engine/run-scenarios.mjs` + `engine/scenarios.json`。
模拟一段跨周训练史 —— 把上一步的建议当成用户**实际练的内容**再喂回去 ——
然后对整条轨迹断言产品红线（`PRODUCT.md` / `docs/interaction-spec.md`）：

| 红线 | 为什么它必须可执行 |
|---|---|
| 理由非空 / **≤ 40 字**（一行放得下） / 不含 null·undefined·NaN | 这三条以前只活在文字里，没有任何东西守着 |
| 双重渐进：**只有做满组数且触到区间上限才允许加重** | 这是引擎的核心契约，向量看不出来（单步看不出"上次"） |
| 单步加重 ≤ 一个步长；重量**只保持或增加，永不下降** | 防止"改一处规则，连练几周后重量失控" |
| 自重动作重量恒为 null 且永不 `linear_progress`（硬红线 2） | 序列里一次都不许破 |
| 按时长动作按 5 秒推进、到上限改说"建议加负重"、理由里不说「次」 | 刚修的那个根因，得有东西守着它不被改回去 |

**两条刻意的取舍**：

1. **不在 Dart 侧再实现一份运行器**。两套实现的一致性由 `vectors.json` 保证（同一份向量、
   两个引擎都必须跑通）。场景 eval 验证的是**规则体系的质量**，不是语言的移植 ——
   再写一份 Dart 运行器只是把同一套红线重算一遍，多出一处会各自漂移的代码。
2. **用户模型刻意不依赖引擎**。模型描述的是"一个人会怎么练"（做满 / 做不满 / 少做一组 /
   断练 25 天），不是"引擎想让他怎么练"。照着引擎输出反推的话，这套 eval 就成了同义反复。

**它凭什么不是装饰**：变异清单里有一条 `runner: 'scenarios'` 的变异体 ——
把回归保护的文案写长到 59 字。向量层（只查子串）**44/44 全过**，场景层把它抓出来。
这条变异体是场景 eval 的**存在性证明**。

**一个教训**：这套 eval 第一次跑报的两条"违规"是**它自己**的 —— 红线写成 `/次/`，
把「**第一次**练这个动作」里的"次"算成了计数单位。修精确成「数字 + 次」与「次数」。
（和变异测试的第一版一样：新工具的第一批产出往往是它自己的毛病。）

## 自检为什么要加"变异测试"（2026-09-29 定）

**问题**：`flutter test`（**当时** 457 项）全绿，但这不证明测试有效。反例就在本仓库里 ——
分析报告指出过："209 项测试全绿，而核心引擎从未在真实路径上运行过"
（`main.dart` 构造控制器时不传 `lastSession`，而测试自己传了）。
**测试数量从来不等于测试有效性。**

**做法**：`tool/mutation.mjs` —— 把源码故意改坏（21 个变异体，覆盖两套引擎 + tap 计量器），
再跑既有的第 1–3 层；测试红了 = 这个变异被杀死，还是绿 = **盲区**。

**三条必须知道的约定**：

| 约定 | 为什么 |
|---|---|
| 在**临时目录**里改源码，绝不碰工作区 | 变异测试会改源码，改真源码的话一次崩溃就把仓库留在坏状态 |
| 编译不过的变异体算 **INVALID**，不算杀死 | 那种"失败"证明不了任何事（第一版就因此跑出过 100% 的假成绩：暂存区少拷了一个 `core/units.dart`，全部 Dart 变异体都在编译期就挂了） |
| 变异点必须**唯一**，否则也算 INVALID | 不唯一的替换会改到一处没被覆盖的地方，跑出来是"存活"，结论完全错 |
| **等价变异体**（语义等价、没有测试能杀）单独标注，不计入得分 | 例如"去掉重量加法的浮点消除"：实测 0.1–400 kg 全范围都不会泄漏噪声，加测试是自欺。把知识留在清单里，比删掉它更好 |

**什么时候跑**：`./verify.sh` 的第 6 层，3.8 秒。它是六层里唯一验证"测试本身"的一层。

## 界面零件为什么也抽共用件：一个 bug 被抄了三遍（2026-10-04 定）

**问题**：胶囊选项（休息时长 / 组数 / 部位…）在仓库里是**三份拷贝**
（`profile_widgets.choicePill`、`routine_screen._chip`、`custom_exercise_screen._chip`）。
同一个 `Container(alignment: Alignment.center)` 写法，在 `Wrap` 里会被**撑成通栏** ——
于是同一个"6 个选项各占一整行"的 bug 也**复制了三份**，而没有任何一行报错
（`Row` / 横向 `ListView` 给的是无界宽度，同一个写法在那儿看着完全正常）。

**做法**：抽到 `app/lib/core/pills.dart`，三处都调它；
`profile_widgets.dart` 用 `export` 转出去，既有调用方的 import 不用动。

**判据不是"看着还行"，是量出来的**：`app/test/pill_layout_test.dart` 把胶囊放进
**固定 360pt 宽**的 `Wrap` 里量真实尺寸，并且**真的开出两个页面**量 `set-5` /
`custom-muscle-chest` 这些真控件 —— 只测组件的话，"组件改好了、页面又抄了一遍旧的"仍然会绿。

**为什么文件里留着两条"旧写法"的对照测试**：它们断言**旧的错写法确实被撑满**（360pt）。
没有它们，"量出来很窄"可能只是量错了地方，守卫会退化成永远绿的摆设 ——
这和 `tool/mutation.mjs` 是同一个道理（**测试数量从来不等于测试有效性**）。

> 这类"共享组件 + 组件级守卫"的做法只对**会被复制**的零件值得做。
> 一个只在一个页面出现的私有 widget 抽出来只会多一层跳转。

## iOS 26 的液态玻璃：为什么自己写桥、为什么只做 iOS（2026-10-06 定）

**决策**：走**原生真材质**（`UIGlassEffect`）、**只做 iOS**，Android 保持原样；
**自己写一个 platform view**（`app/ios/Runner/GlassBridge.swift` + `app/lib/core/glass_surface.dart`），
**不引第三方包**。

**为什么不用 pub 上那两个包**（`native_liquid_glass` / `liquid_glass_renderer`）：
* 一个**未验证发布者**（12 likes / 2.58k 下载），一个**自标 experimental**（还有显存尖峰的已知问题）；
* 我们只要"一块玻璃"，用不上它们那二十个控件；
* **引依赖的账很贵**：政策 §三之五 SDK 表（中英）· Play 数据安全 · App Store 隐私标签 ·
  `privacy-facts.json` · 164 号文双清单 —— 一处都不能少。自己写这 100 行，这笔账一笔都不用记。
  这与仓库一贯做法一致（通知、Live Activity、休息提示都是自己写的桥，当初就是为这个）。

**为什么只做 iOS**：Android 上这条材质根本不存在；用户拍板"Android 一个像素都不动"。
实现上由 `GlassSurface` 兜住 —— **非 iOS 原样返回 `child`**（不模糊、不加边、不加内边距），
所以这条线断了会有测试红（`app/test/glass_surface_test.dart`）。

**"溶在一起"是个陷阱（2026-10-06 当天纠正了一次）**：`UIGlassContainerEffect`
听起来正是"把两块玻璃合成一块"、也正是用户看参考图时想要的那个词，但真机上它的实际表现是
**把叠在一起的两块玻璃抹平成一块** —— 选中胶囊的亮边与凸起全没了（底托与胶囊同高时，
屏幕上**什么都看不出来**）。用户的原话："切 tab 的时候完全感觉不到玻璃的感觉。"
同一组参数只把容器去掉，胶囊立刻变成一块**有亮边的凸起玻璃**。
逐行对比（同一屏幕、只改一个参数）：`docs/images/glass-probe-segment-variants.png`
（D 行 = 有容器，A/B 行 = 独立两块）。

所以现在：**底托与选中胶囊是两块各自独立的玻璃**（`GlassSegmented`），
胶囊比底托**往里缩 5pt**（这条缝就是"凸起来那块"的分界）+ **一点白（默认 `#FFFFFF1F`）** ——
那一点白是"选的是它"唯一的提示，因为**玻璃底托本身就比屏幕亮**，选中的那块必须再亮一档
（苹果自己的做法也是这样）。代价：切换时不再有"融合"的形变（苹果自己的分段控件也是
"一块独立的选中玻璃"）。实现在 `app/ios/Runner/GlassBridge.swift` 的
`GlassSegmentedPlatformView`（**几何在原生侧算，所以条目必须等宽** ——
Dart 那边由 `GlassSegmented` / `GlassSegmentedRow` 保证，`glass_segmented_test.dart` 钉住）。

**按压反馈（2026-10-06 你追加的"按压下去要有参考图里那种圆按钮"）**：
苹果那套叫 **交互玻璃**（`UIGlassEffect.isInteractive`）—— 手指按住时玻璃会"果冻"式地形变。
但我们的平台视图在 **Flutter 内容下面**（标签/图标是 Flutter 画的、盖在它上面），
UIKit 收不到触摸 → **原生那套反应根本触发不了**（试过：`isInteractive` 打开也没用）。

替代做法（观感一致、又不动点击与旁白那条链路）：
`GlassSegmented` 用 `Listener` 盯着指针（只观察、不进手势竞技场），把"按在第几格/松开了"
通过通道发给原生，原生演形变。**按住时那颗玻璃跑到手指那一格并鼓出边界、松手弹回来。**
按下与松手是两条不同的弹簧曲线（`damping 0.32 / 初速 1.0` 按下去会真的过冲一下，
`0.62 / 0.35` 松手时轻轻回弹）。底栏在 iOS 上**同时关掉 Material 的水波纹**
（`NoSplash` + 透明高亮）—— 那是 Android 的语言，一层涟漪会把玻璃的形变糊掉。

**这一套是照着你 2026-10-06 的第二轮反馈定的三条**（每条都有实测依据）：
1. **幅度**：按住时每边再鼓 **14pt**（`pressBulge`），所以它会**超出底栏边界**约 9pt
   —— 老参数只鼓 3pt 且被夹在边界里，你的原话是"太小了 要超出边界"；
2. **通透度**：选中胶囊的材质是 **`.clear` + 默认一点白都不染**（底托才是 `.regular`）。
   2026-10-06 你追问"鼓起来那一块能不能做成全透明的"之后定为**完全不染色** ——
   实测那颗反而更像苹果：形状是靠**边缘折射**读出来的，不是靠一层白
   （对比图 `docs/images/glass-probe-transparent.png`：第 0/3 行不染色，第 1/2/4 行染色）。
   代价是"选中的是谁"完全交给**图标/文字的颜色**（底栏的橙色）与玻璃的边缘高光 ——
   平底卡片上的那两行单位是例外（背后没有内容可折射），仍然留一点白。
   老写法的问题：
   两块 `.regular` 叠在一起是**双重磨砂** → 鼓起来那颗成了"奶白疙瘩"，
   你的原话是"通透度太差了 完全不是透明的"。按下时也只把染色提亮 15%（老参数 ×1.8 是刷白）；
3. **Q 弹**：老参数阻尼 0.55 把弹簧压死了，现在按下去真的会过冲再收。

逐行对比（同一屏、只改参数）：`docs/images/glass-probe-press-variants.png`
（第 0 行平时；第 1/2 行 `regular` 的鼓包=奶白；第 3/4 行 `clear` 的鼓包=透得过去的圆按钮）。
按住时实拍：`docs/images/glass-press-tab.png`（平时 / 按住「数据」/ 松手后）与
`docs/images/glass-press-segmented.png`（分段控件：按住 / 松手后）。

**按下去"两滴水滴融在一起"（2026-10-06 第四轮，你纠正了我一次）**：
我第一版理解成"按住时那一格鼓成一个圆按钮"，你的意思是 ——
**按住时相邻两格之间要有"融"的感觉，像两滴水滴合成一滴**。所以现在：

* 底托在外，**胶囊与"第二颗水滴"在同一个 `UIGlassContainerEffect` 里**
  （容器只装这两滴：底托包住它们，混进去会被一起抹平 —— 就是当天早些时候那个坑）；
* 按住**别的那一格**时，手指底下冒出**第二颗水滴**（跟手指走，`press` 消息里带坐标；
  手指横向移动还会 `pressMove` 实时更新），它和胶囊的距离进了容器的
  `spacing = 34` → 苹果在两滴之间**长出一道"脖子"**，看起来就是两滴水在融；
* 松手那一刻**不马上收水滴**：等"换到哪一格"的消息（`setIndex`）到了，
  **两滴一起滑到新那一格、落到一起之后再收掉一颗** —— 于是收尾是"两滴融成了一滴"，
  而不是"一滴消失、另一滴跳过去"。没人来（按了又滑走）才淡出 = 两滴分开；
* 按住**当前这一格**时不冒水滴，仍然是"鼓起来"（你上一轮要的那个 Q 弹幅度）。
* 顺带把**按住不放、横向拖到别格再松手 = 换 tab** 做出来了（Dart 侧比对
  "按下那格"与"松手那格"，不同才回调 `onDragSelect`；普通点击走原来那条 tap，不会重复触发）。

证据（同一屏四态，按时间顺序）：`docs/images/glass-drop-merge.png`
（平时 / 按住当前格 / 手指移到相邻格=两滴融合 / 松手后合成一滴）。

**切 tab 的过渡：可拖的 `PageView` + 玻璃跟手（2026-10-06 你追加的第二条）**：
你原来的感觉是"切 tab 没有那种丝滑的过渡、没有左右拖动的感觉" —— 因为那时外壳是
**直接换一屏**（`_bodyFor(_tab)`，一个像素都不动就换完了）。现在 iOS 上外壳换成：

* **`PageView`（可以左右拖着换 tab）** —— 手指拖到一半松手，按页吸过去；
* **底栏那颗玻璃跟着手指滑**：`PageController` 每帧把"当前停在第几页"（小数，例如 0.6）
  通过通道喂给原生（`setIndexFraction`），原生按 `w × 小数` 摆胶囊 ——
  所以拖动时它是**连续移动**的，不是跳格（实拍 `docs/images/glass-swipe-pill-follows.png`：
  页面滑到一半，胶囊正好停在两格中间）。松手落页后交回"整格"轨道（`setIndex`）；
* **点 tab** 走另一条路（`_selectTab`）：图标颜色**立刻**变（等动画跑完再变会显得钝），
  页面 `animateToPage` 滑过去（远的 tab 给更长的时间，不然四页在 300ms 里一闪而过），
  这趟动画期间**不喂拖动位置** —— 两边同时驱动会打架、看起来是抖。

⚠️ **这一条只在 iOS 上开**：Android 仍然是"直接换一屏"（判据还是
`GlassSurface.isSupportedPlatform`，与你"Android 一个像素都不动"那条一致）。
要给 Android 也加上只是同一个条件的事 —— 但那是**行为**改变，得你点头。

**玻璃会折射它背后的字 —— 所以格子里的文案必须由原生画（2026-10-06，用户备忘条第 2 条）**：
用户报的是「重量单位这里显示 bug」。真机/模拟器上的现象是**同一行字出现两份**：
一份清晰（Flutter 画的，位置对），一份错位发虚（玻璃把同一份字**折射**出来的）。
根因：**iOS 的平台视图永远盖在 Flutter 内容之上**，所以"玻璃在上、Flutter 的字在它背后"
是必然的 —— 而液态玻璃的本职就是**折射背后的东西**，于是我们自己的字被折射成了第二份。

**修法**：格子里的字（底栏的图标+文字、分段控件与单位行的标签）**交给原生画**
（`GlassSegmentedPlatformView` 里的 `labelsBox`：UILabel / SF Symbol，加在玻璃**之上**、
同一个平台视图里）——字画进玻璃里面，就没有第二份可折射。Dart 那一份只留布局、点击热区
与语义（`Opacity(0)`），所以测试里的 `find.byKey` / 点击 / 旁白全都不变。
顺带：底栏图标换成了 **SF Symbol**（`dumbbell.fill` 那五个），比 Material 图标更像苹果；
选中那一格的图标粗细也跟着换一档（苹果自己的做法）。

**开关（同一天的第 3 条）**：iOS 上**用系统的 `UISwitch`**（`lianleme/switch` 这个平台视图），
它在 iOS 26 上**自带**液态玻璃。自己拿 UIView 仿是下策：材质、按压回弹、旁白都要重写，
而且永远差一点。Android 仍然是 Material 开关（一个像素都不动）。

**两条 spike 实测出来的设计规矩**（证据 `docs/images/glass-spike-*.png`）：
1. **玻璃必须背后有东西可折射** —— 纯炭黑上 `.regular` 会变成一块浅灰板。所以底栏是**浮在内容
   之上**的（`main.dart` 里 iOS 走 `Stack`：内容 `Positioned.fill`、底栏 `Positioned` 浮着），
   滚动时真实内容从它背后经过 —— 这就是它折射的东西。**不再自己垫一层渐变**：垫出来的只是
   一条"贴着底的浅色带"，2026-10-06 已删（当初那么做是因为外壳把底栏排在内容**下面**，
   压根没有东西可折射）；
2. **平底（纯色卡片）上不要用 `.regular`** —— 那两行单位在卡片的平底上，背后没有内容经过，
   所以用 `.clear` + 一点点白（底 `#FFFFFF14`、选中胶囊 `#FFFFFF2E`）。**同一套控件在两处
   用不同材质是有意的**，不是漏改。

**材质现状**：底栏 = `.regular`、不加 tint（用户 2026-10-06 反馈"亮度不够"，但**先不动**，
看"融合"这一改之后的观感再定）。为调材质临时加的 `LIANLEME_GLASS_STYLE` / `LIANLEME_GLASS_TINT`
两个 `--dart-define` 旋钮已删 —— 留着就是给下一个人一个不知道什么时候该拧的开关。

**还没验的三件事**（别当成已验）：① 真机 release 的帧率（platform view 有整屏合成代价）；
② iOS 26 以下的退回形态（本机只有 iOS 27 运行时，桥里退回 `UIBlurEffect(.systemUltraThinMaterial)`）；
③ 真机上"融合 + 滑动"的手感与观感（这一版刚装上，用户还没看）。

## 补签为什么要新开一张表（2026-10-06 定）

**背景**：第二部分第 2 条「连续保护（补签）」——每周一次、代价是本周至少练过 1 次、
补签不涨连续天数只防断。

**决策**：新开一张表 `streak_protection`（v21 迁移），**一行 = 被保护的一天**。

**为什么不能"改一下历史就好了"**（最自然的那个做法，也是最错的一个）：
补签的字面意思像是"把那天补成练过了" —— 于是有人会想在 `set_record` 里插一组、
或者在 `workout` 上改个时间。**不行**：整个 App 的底线是**记录就是事实**
（徽章、连续天数、段位、周报、经验、部位平衡全都是从记录推导出来的）。
一旦某天"其实没练"而库里写着练了，那条假记录会同时污染：容量、PR 榜、
部位平衡、周报里的"练了几天"、以及**下一年的同一天**（跨年回看时它还在那儿）。

**所以补签必须是一次单独的声明**：「我知道那天断了，我选择不让这条链断在这里」。
它是这个 App 里**唯一一件用户写下来的、关于历史的东西**，值得一张自己的表。

**表形状与代价**（为什么不是"存一个计数"）：
`date`（被保护的那一天，主键）+ `created_at_ms`（补签这个动作发生的时刻）。
额度**由已补的那一天反推**（周一那天所在的周）—— 存一个"本周已用次数"的计数，
它就会和这张表本身不一致（两张数据说同一件事，迟早会分叉）。

**连带影响（新加表的四步，这一步在别的决策里没写过）**：
① `db.dart` 加表 + 注册 + `schemaVersion` +1 + `onUpgrade` 链尾；
② `dart run build_runner build` 重生成 `db.g.dart`（它 `.gitignore` 了）；
③ `deleteAllUserData()` 里删掉它（删除权）；
④ `test/delete_all_test.dart` 的**表清单守门** + `seedEveryUserTable()` 各加一条。

**如实交代的那一句**：补签撑住的那一天**计 1 天**（否则"接上"就没有意义），
所以界面上必须同时写「已连续打卡 N 天（**其中 M 天是补签**）」——
不写就等于告诉用户"这些天我天天都练了"。这一句由
`streakLabelWithProtection()` 生成，有测试钉着。

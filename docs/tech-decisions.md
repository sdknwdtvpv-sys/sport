## 客户端：Flutter + 原生 Swift 扩展

| 选择 | 理由 |
|---|---|
| **Flutter 而非 RN** | 一套渲染管线，双端像素级一致。`less is more` 的设计经不起两端体验漂移，也不该维护两套 UI 分支。60fps 列表与自绘图表完全可控 |
| **本地优先：drift (SQLite)** | 响应式查询 + schema 迁移成熟，训练中零网络依赖（见 `data-model.md` 的同步设计） |
| **Apple Watch 用原生 Swift 扩展** | **手表独立 App 双端框架无解，必须原生**。MVP 不做手表独立 App，只做 HealthKit 读写 |
| **Android 侧** | 对接 Health Connect，替代 HealthKit |

> **备选 RN 也完全成立** —— 训记本身就是 RN（包名 `com.trainnote.rn`），在该场景已被验证。若团队是 JS 背景，选 RN 的成本远低于切 Flutter。**这条取决于团队的人，不取决于技术优劣。**

**为什么"双端"反而强化了 Flutter 的理由**：单端时你可以为 iOS 做精细打磨、Android 稍差也能接受；双端同步上线意味着两端的体验差距会直接暴露，而本产品的核心资产恰恰是"一致的省事感"。

## 服务端：一期做到极薄

- 只做三件事：**账号、增量同步、云备份**
- Postgres + REST，不做实时协同、不做服务端计算
  > ⚠️ 2026-09-30 核对：**一期实现用的是 `node:sqlite` + 零依赖 HTTP**（不是为了省事，
  > 是为了「本地就能跑通并自检」）。换 Postgres 时只改 `server/backend-store.mjs` 一个文件，
  > 见 `docs/backend-design.md` §七之五。
- **规则引擎跑在客户端**：离线可用、零延迟、零推理成本（健身房地下层没信号，这个选择是被场景逼出来的，不是技术偏好）

## 合规（容易被忽略的坑）

1. **HealthKit 数据禁止用于广告或出售**（App Store 审核 5.1.3），隐私政策必须显式写明用途
2. 国内上架需要隐私政策 + 个人信息收集清单；**健康数据属敏感个人信息**，单独同意
3. 用户数据必须支持**一键全量导出**与**账号注销删除**
4. 同步接口不得上传动作视频/照片（一期不采集，规避风险）

## 为什么还要一层"场景级 eval"（2026-09-29 定）

**问题**：`engine/vectors.json` 的向量管的是**单步正确性** —— 给一个输入，输出对不对。
但用户感受到的不是单步，是"**连练 12 周之后，这个 App 说的话还讲不讲道理**"。
每一步都正确的函数，串起来照样可能走成荒谬的轨迹（这正是分析报告里那句
"209 项测试全绿，而核心引擎从未在真实路径上运行过"的同类问题，只是换了层次）。

**做法**：`engine/run-scenarios.mjs` + `engine/scenarios.json`。
模拟一段跨周训练史 —— 把上一步的建议当成用户**实际练的内容**再喂回去 ——
然后对整条轨迹断言产品红线（`PRODUCT.md` / `docs/interaction-spec.md`）：

| 红线 | 为什么它必须可执行 |
|---|---|
| 理由非空 / **≤ 40 字**（一行放得下） / 不含 null·undefined·NaN | 这三条以前只活在文字里，没有任何东西守着 |
| 双重渐进：**只有做满组数且触到区间上限才允许加重** | 这是引擎的核心契约，向量看不出来（单步看不出"上次"） |
| 单步加重 ≤ 一个步长；重量**只保持或增加，永不下降** | 防止"改一处规则，连练几周后重量失控" |
| 自重动作重量恒为 null 且永不 `linear_progress`（硬红线 2） | 序列里一次都不许破 |
| 按时长动作按 5 秒推进、到上限改说"建议加负重"、理由里不说「次」 | 刚修的那个根因，得有东西守着它不被改回去 |

**两条刻意的取舍**：

1. **不在 Dart 侧再实现一份运行器**。两套实现的一致性由 `vectors.json` 保证（同一份向量、
   两个引擎都必须跑通）。场景 eval 验证的是**规则体系的质量**，不是语言的移植 ——
   再写一份 Dart 运行器只是把同一套红线重算一遍，多出一处会各自漂移的代码。
2. **用户模型刻意不依赖引擎**。模型描述的是"一个人会怎么练"（做满 / 做不满 / 少做一组 /
   断练 25 天），不是"引擎想让他怎么练"。照着引擎输出反推的话，这套 eval 就成了同义反复。

**它凭什么不是装饰**：变异清单里有一条 `runner: 'scenarios'` 的变异体 ——
把回归保护的文案写长到 59 字。向量层（只查子串）**44/44 全过**，场景层把它抓出来。
这条变异体是场景 eval 的**存在性证明**。

**一个教训**：这套 eval 第一次跑报的两条"违规"是**它自己**的 —— 红线写成 `/次/`，
把「**第一次**练这个动作」里的"次"算成了计数单位。修精确成「数字 + 次」与「次数」。
（和变异测试的第一版一样：新工具的第一批产出往往是它自己的毛病。）

## 自检为什么要加"变异测试"（2026-09-29 定）

**问题**：`flutter test`（**当时** 457 项）全绿，但这不证明测试有效。反例就在本仓库里 ——
分析报告指出过："209 项测试全绿，而核心引擎从未在真实路径上运行过"
（`main.dart` 构造控制器时不传 `lastSession`，而测试自己传了）。
**测试数量从来不等于测试有效性。**

**做法**：`tool/mutation.mjs` —— 把源码故意改坏（21 个变异体，覆盖两套引擎 + tap 计量器），
再跑既有的第 1–3 层；测试红了 = 这个变异被杀死，还是绿 = **盲区**。

**三条必须知道的约定**：

| 约定 | 为什么 |
|---|---|
| 在**临时目录**里改源码，绝不碰工作区 | 变异测试会改源码，改真源码的话一次崩溃就把仓库留在坏状态 |
| 编译不过的变异体算 **INVALID**，不算杀死 | 那种"失败"证明不了任何事（第一版就因此跑出过 100% 的假成绩：暂存区少拷了一个 `core/units.dart`，全部 Dart 变异体都在编译期就挂了） |
| 变异点必须**唯一**，否则也算 INVALID | 不唯一的替换会改到一处没被覆盖的地方，跑出来是"存活"，结论完全错 |
| **等价变异体**（语义等价、没有测试能杀）单独标注，不计入得分 | 例如"去掉重量加法的浮点消除"：实测 0.1–400 kg 全范围都不会泄漏噪声，加测试是自欺。把知识留在清单里，比删掉它更好 |

**什么时候跑**：`./verify.sh` 的第 6 层，3.8 秒。它是六层里唯一验证"测试本身"的一层。

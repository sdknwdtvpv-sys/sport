# 引入「微信登录」可行性报告

> 2026-10-01 出。**结论先行，依据在后**，来源分「官方原文」与「社区口径」。
> 背景：练了么目前**完全没有账号体系**（数据在本机 + 匿名恢复码式云备份），
> 商业化打算走「买断 Pro → 云备份订阅 → AI」（见 `docs/monetization-plan.md`）。
> 这篇回答的是：**要引入微信登录，得付出什么、会碰到哪些硬约束。**

## 一、结论（能不能做、值不值得做）

**能做，但不该作为第一步；而且它不是一个"登录方式"，而是一次"账号体系改造"**，会同时牵动：

1. **主体资质**：微信开放平台的实际门槛高于"注册一个账号"（下详）；
2. **iOS 审核硬约束**：Apple 审核指南 **4.8 明确把 WeChat Login 列为触发条件** ——
   用微信登录就必须**再提供一个等价登录选项**（Sign in with Apple 满足），
   而我们的健身 App **不落入 4.8 的任何一条例外**；
3. **合规面**：有账号就必须有**应用内注销**（《认定方法》第六条，15 个工作日时限），
   隐私政策/收集清单/商店表单/软著说明书都要跟着改；
4. **服务端**：`AppSecret` 与 token 交换**必须放服务端**（这是微信的硬要求），
   我们的"极薄后端"要新增一张账号映射表与一个接口；
5. **它并没有解决"跨平台权益"**：iOS 微信登录与安卓微信登录能拿到同一个 `unionid`
   （前提是同一个开放平台账号下的两个移动应用），这才真正解决跨端 —— **这是它唯一
   强于「恢复码」的地方**。

**我的建议**：
* **P0 不做**。跨设备找回继续用**恢复码**（已有、零成本、无隐私面）；
* **P1 若要做**，一次做三件套：**免登录（默认）+ Sign in with Apple（满足 4.8）+ 微信登录（国内主转化）**，
  服务端只存 `unionid / Apple sub → 本机匿名账号` 的映射；
* **先拿到付费开发者账号**（免费档用不了 Associated Domains，微信登录在 iOS 上根本联调不了）。

## 三、接入流程（从零到能登录）

1. 注册微信开放平台账号 →（**认证**）；
2. 创建**移动应用**：填名称/简介/官网/图片/上架信息/类目/流程图；
   开发信息「至少填一种」：**Android 签名 + 包名**、**iOS Bundle ID + Universal Links**。
   审核 **1–7 个工作日**。
3. 拿到 `AppID` / `AppSecret`（**AppSecret 只能放服务端**）。
4. 客户端 SDK 拉起授权（`SendAuthReq.scope` **只能填 `snsapi_userinfo`**，没有静默模式）→ 拿 `code`（10 分钟一次性）。
5. 服务端 `GET /sns/oauth2/access_token` 用 `code` 换 `access_token`(7200s) / `refresh_token`(180 天) / **`openid` + `unionid`**
   （官方说明：**只做账号识别不需要再调 `/sns/userinfo`**）。
6. 把 `unionid` 映射到你自己的账号记录 → 发自己的会话凭据。

> 官方文档：[创建移动应用](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/guideline/create.html)、
> [微信登录开发指南](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/WeChat_Login/Development_Guide.html)

## 四、能拿到哪些用户信息（决定"要不要头像昵称"）

| 信息 | 现在还能拿吗 | 依据 |
|---|---|---|
| `openid` / `unionid` | ✅ 能，且是**唯一稳定**的标识 | 官方：`access_token` 接口直接返回 |
| 昵称、头像 | ✅ 仍返回，但微信合规口径表述为「**用户主动选择的**微信头像、昵称」 | 官方：[Open SDK 合规使用指南](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/agreement/sdk.html) |
| 性别、地区 | ❌ **2021-10-20 起不再返回** | 官方：[授权后接口调用](https://developers.weixin.qq.com/doc/oplatform/Mobile_App/WeChat_Login/Authorized_API_call_UnionID.html) |
| 手机号 | ❌ **移动应用没有这个能力**（手机号快速验证组件只存在于**小程序/小游戏**） | 官方文档只在小程序侧有该组件；移动应用侧未找到 |

**这条很关键**：如果原来的想法是"微信登录顺便把手机号拿到"，**那条路在移动应用上不存在**。
我们要么不要手机号，要么另做短信验证码（成本与合规负担都更重）。

## 五、Flutter / 双端要配什么

* SDK 选型：`fluwx`（社区主流封装，仍在维护；**注意 V6 是破坏性升级**）。
* **Android**：开放平台登记的**签名 + 包名**必须与正式包一致（用 debug 签名登记、正式包签名不同 → 调不起来）；
* **iOS 三件套**（缺一不可）：
  1. **Universal Links**（https、**必须带 `/*` 通配符**、paths 不能带 query）——
     ⚠️ 它需要 **Associated Domains** entitlement，而**免费 Apple ID 用不了这个 entitlement**，
     所以微信登录在 iOS 上**必须等付费开发者账号**；
  2. URL Scheme；
  3. `LSApplicationQueriesSchemes`（**iOS 15 起只生效前 50 个**）。
* 微信还要求 **SDK 延迟初始化**（用户同意隐私政策前不得 init）——我们的同意门正好是这个顺序，
  但要注意"同意之前不能碰 SDK"。

## 六、iOS 审核：这是最大的一条风险

* **Apple 审核指南 4.8**：官方原文**直接把 `WeChat Login` 写进了触发条件** ——
  使用第三方/社交登录时，必须**同时**提供一个"只收集姓名+邮箱、允许隐藏邮箱、不用于广告"的
  等价登录选项（**Sign in with Apple 符合**）。
* **例外共 5 条**（自有账号体系、替代应用市场、教育/企业账号、政府 eID、特定第三方服务客户端）——
  **我们这种健身工具 App 不落入任何一条**。
* **5.1.1(v)**：核心功能与社交网络无关时，**必须允许不登录使用**；
  **只要提供了账号创建，就必须提供 App 内账号删除**；还必须能**撤销社交凭据**。

**结论**：微信登录 + Sign in with Apple **必须成对出现**，且"免登录可用"是硬要求 ——
这与我们的产品姿态其实一致（我们本来就该免登录），但**工作量不是加一个按钮**：
它意味着账号体系、注销流程、凭据撤销、隐私政策新增章节一起做。

## 七、国内合规

* **注销入口 + 15 个工作日处理时限**是硬要求（《App 违法违规收集使用个人信息行为认定方法》第六条）；
* 微信要求隐私政策**按模板披露 SDK**（含 iOS 剪贴板权限），且**同意前不得初始化 SDK**；
* **《移动互联网应用程序信息服务管理规定》第六条的实名义务以"提供信息发布、即时通讯等服务"为前提** ——
  工具类健身 App **不在范围内**；网上流传的"所有 App 都要后台实名"是**扩大解读**；
* 真要做实名（例如未来上社区功能），那是另一个量级的事。

## 八、替代方案对比

| 方案 | 国内可用 | 成本 | 审核风险 | 我的评价 |
|---|---|---|---|---|
| **恢复码（现有）** | ✅ | 0 | 无 | **P0 就用它**：跨设备找回够用，零隐私面 |
| **Sign in with Apple** | ✅（iOS 可用；安卓要自建网页流程） | 低（免费档可惜用不了该 entitlement，**要付费账号**） | 无（它本身就是 4.8 的答案） | **P1 必做**（如果做第三方登录） |
| **微信登录** | ✅（国内转化最好） | 中高（资质 + 认证 + 服务端 + 双端配置） | **中高（4.8）** | P1 做，但必须与 Apple 登录成对 |
| **Google 登录** | ❌ 国行无 GMS | —— | —— | 不做 |
| **手机号验证码** | ✅ | 高（短信费用 + 实名 + 合规） | 中 | 不做（移动应用也拿不到微信手机号） |

## 十、需要你决定的四件事

1. **要不要走"账号体系"这一步**？我建议：**P0 不做**，等买断 Pro（`monetization-plan.md` 阶段 P0）跑出付费意愿再评估；
2. 若做：**是否同时上 Sign in with Apple**（不做的话 iOS 必被 4.8 拒）；
3. 若做：**主体用个人还是公司**（认证与类目在实践上偏企业，且需要营业执照）；
4. 若做：**我们自己的账号体系要不要**（微信/Apple 只提供身份，权益与数据归属仍要落在我们这儿）——
   我建议**不做自建账号**：`unionid/sub` 直接当我们内部的 `user_id` 用就够了，别收手机号邮箱。

# 健身搭子（社交）可行性与方案（2026-10-10）

> 用户 2026-10-10 点单：「如果后期想上社交功能好实现吗？我觉得健身搭子是个很必要的功能」。
> 这一页回答**可行性**（"好实现吗"要分四层回答，成本差 5–10 倍）并给出**方案**。
> **本文只是方案，没有动代码。**
>
> ⚠️ 先说清楚：这个需求与**三处既有决定正面冲突**，需要你先明确一次（见 §〇）。

---

## 〇、与既有决定的冲突（必须你点头，不然做出来就是自相矛盾）

| 时间 | 说法 | 出处 | 与"搭子"的关系 |
|---|---|---|---|
| 2026-09 | **不做社区 Tab**："一期的社交用训练结束生成一张分享卡 → 微信替代，成本极低、不引入内容运营负担" | `PRODUCT.md` §4 | 🟡 **不必然冲突**：搭子可以做成"一对一、不发布内容"，那就不是社区 |
| 2026-09 | **明确不做**：社区 / 排行榜 / 好友 | `docs/feature-backlog.md` 四 | ❌ **直接冲突**（"好友"就在里面）。要改成"好友**关系**做、**动态/排行/公开内容**不做"，这一条得改 |
| 2026-10-06 | 用户拍板徽章与留存玩法时定的三条红线之一：**不引入社交上传**（不分享到平台、**不加好友**、不上传成绩） | `docs/plan-badge-redesign.md:9` | ❌ **直接冲突**（"不加好友"）。那是**那一批**的红线（当时的语境是"留存玩法不靠社交"），现在你主动提出来，应当以新决定为准 |

**我的建议口径**（写成一句话，后面全部按它施工）：

> **搭子 = 一对一的责任伙伴**：只看得到你**自己选择分享**的**结构化状态**（练没练、练了哪个部位、连续几天），
> **没有动态流、没有公开内容、没有排行榜、没有聊天**。
> 也就是：**"好友关系"要做，"社交上传"仍然不做** —— 这样 `PRODUCT.md` §4 那条"不做社区"依然成立。

**需要你确认的**：① 上面这个口径你认不认；② `feature-backlog.md` 四里"好友"那一项改成"（1:1 搭子做，社区/排行不做）"；③ `plan-badge-redesign.md:9` 那条红线改成"不引入**公开**社交上传（搭子是一对一、用户主动选分享范围）"。

## 一、先把三件事分开（它们的成本差 5–10 倍）

| 事 | 是什么 | 面积 | 成本 | 合规负担 |
|---|---|---|---|---|
| **A. 搭子（责任伙伴）** | 一对一：互相同意 → 看到对方"今天练没练 / 连续几天 / 哪个部位" → 可以互相催一下 | 小 | **8–16 人日**（L0+L1+L2） | 低→中（看有没有推送、有没有自由文本） |
| **B. 好友/关注 + 动态流** | 多人关系 + 内容流（别人看你发了什么） | 中 | 25–40 人日 | **高**（UGC：过滤/举报/拉黑/响应时限 + 运营） |
| **C. 社区 Tab / 排行榜** | 公开广场、榜单、挑战赛 | 大 | 60+ 人日 + 常年运营 | **很高**（内容审核 + 未成年人 + 实名 + 备案） |

**你要的"搭子"是 A**。A 能做，而且不算贵；**B/C 才是那个"一上就回不了头"的东西** ——
它们把产品从"工具"变成"平台"，随之而来的是内容审核义务与运营人员成本（`PRODUCT.md` §4 当初拒绝的正是这个）。

| 分享卡（把邀请发出去） | ✅ 有 | `app/lib/features/summary/share_card.dart`（360×520 图 + 导出分享），把它升级成"带邀请码的卡"即可 |
| **站内通知中心** | ✅ 有 | `AppNotification` 表 + 通知中心屏（本地生成）。**"搭子今天练了"可以走站内通知，不需要推送** —— 这是省钱的关键 |

| 实时/增量同步 | ❌ 没有 | 一期只有快照式备份；搭子状态不需要实时，**用"打开时拉取"就够** |
| 内容审核能力 | ❌ 没有 | **所以设计上要避免自由文本**（见 §四） |

## 三、四层方案（**按层拍板，别一次全要**）

### L0 · 邀请（"把搭子拉进来"）—— **2–3 人日**

* 用户看到：训练总结页/我页多一行「邀请搭子」→ 生成一张**带邀请码的分享卡** → 系统分享面板发出去；
* 对方看到：点开卡片或链接 → 落地页（静态，`/i/<code>`）→ 「下载练了么」→ 装好后在 App 里**输入邀请码**；
* 服务端加：`buddy_invites(code_hash, owner_account, created_at, expire_at, used_by)` + 两个端点（建码 / 核销）；
* 复用：一次性码那套（哈希、一次性、限速、绑账号）+ 分享卡渲染 + 静态落地页；
* 合规：无（就是"分享一张图 + 输一个码"）；
* 判据：`buddy_invite_test.dart`（一码一用、过期不可用、限速、不能邀请自己、非登录态不给建码）。

### L1 · 搭子关系 + 结构化状态互看（**拉取式，不做推送**）—— **4–6 人日**

* 用户看到：我页新增「搭子」入口 → 列表（每人一行：昵称 · 今天练没练 · 连续 N 天 · 上次训练在几天前）；
  对方那一行下面一个「催一下」按钮（**这一版点了只发站内通知，不推手机**）；
* 服务端加：`buddies(a_account, b_account, created_at, state)` + `buddy_days(account_id, day, trained, muscles)`（**只存"练没练/哪些部位"，不存重量、不存身体数据、不存备注**）+ 拉取端点；
* 客户端加：搭子页 + **分享范围设置**（默认：只共享"今天练没练"；可选：连续天数 / 部位；**永远不共享**：重量、组数、体重、身体数据、备注）；
* **最小 UGC 套件（必须有，见 §五）**：搭子行上的「举报」与「拉黑」、共享关闭、「管理规则」静态页、一个公开联系邮箱。
  ⚠️ **不许赌"结构化数据不算 UGC"这条豁免**（Apple 没有给过书面豁免，实务上审核员看的是可观测功能）；
* ⚠️ **昵称不进服务端**：搭子列表里显示的名字，是**用户自己在本地给对方起的备注**（像通讯录备注），
  服务端只认账号 id。这一步顺手绕掉两件事：昵称/头像属于 UGC（Apple 1.2 四项全适用，还要按国内规定核验
  "含中国/国家/国旗"这类字样），以及"服务端多存一份用户内容"。
* 复用：站内通知中心（"小A 今天练了，你也去"是**本机拉取后生成**的站内消息，零推送成本）；
* 合规/隐私：**搭子关系是"向第三方提供个人信息"** → 要有自己的单独同意（照身体数据那道门），并写进政策；解除关系即停止共享；
* 判据：`buddy_status_test.dart`（只发白名单字段、撤回后拉不到、解除后对方看不到、默认范围最小）、`buddy_consent_test.dart`（没同意过不建立关系）。

### L2 · 真的"催到手机上"（推送）—— **4–6 人日（仅 iOS）+ 国内安卓另算**

* 需要：`device_tokens`（在现有 `devices` 上加列或新表）、APNs 密钥与发送逻辑、**限频与反骚扰**（每人每天最多被催 1 次、同一对搭子 24 小时内只推 1 次、可一键静音）；
* 合规：推送内容**不带对方的具体训练数据**（只写"你的搭子催你去练"），避免把他人健康信息写进通知；
* 国内：APNs 不适用，需接 华为/小米/OPPO/vivo 推送（各 1–2 人日 + 各渠道资质）→ **建议国内先不做 L2**，用 L1 的站内通知 + 打开 App 时看到；
* 判据：`buddy_nudge_test.dart`（限频命中、被拉黑/解除后不推、静音生效）。

### L3 · 动态流 / 聊天 / 排行榜 —— **明确不做（这一版）**

* 为什么不做：一旦有自由文本或公开内容，就进入 **UGC 治理**：内容过滤、举报、拉黑、限时响应、未成年人保护、
  国内的内容安全与实名要求…… 那是"运营一个平台"的成本，不是"加一个功能"的成本（§五 有逐条）；
* 什么时候再谈：**用户量到 10 万级、且有人专门做内容与客服** 时再谈。在那之前，搭子（A）已经能吃掉 80% 的"社交感"。

## 四、数据与隐私设计（这一节是搭子能不能做成的关键）

| 原则 | 具体做法 |
|---|---|
| **最小化** | 只共享"结构化的事实"：今天练了没有 / 哪些部位 / 连续天数。**不共享**重量、组数、RPE、身体数据、备注、训练时长 |
| **默认关** | 搭子功能默认关闭；建立关系必须**双方**同意；分享范围默认**最小**（只有"练没练"），逐项 opt-in |
| **单独同意** | 向另一个用户提供你的训练事实 = PIPL 意义上的"向第三方提供个人信息" → 独立同意弹层（照 `body_metric` 那道门的写法），文案写明"对方会看到什么、看不到什么" |
| **随时撤回** | 解除关系 / 关掉共享 = 立即停止；对方**再也拉不到**（要有测试）；政策里写明保留期 |
| **不碰通讯录** | **不要**通讯录权限。Apple 允许"逐个选联系人"，但同一批规则还禁止"全选"、禁止拿通讯录**自建联系人库**、要求发送前预览文案（5.1.1(iii) / 5.1.2(iv)(v)）—— 一整套麻烦换来的只是"少输一次码"。邀请靠分享 + 输码，不扫通讯录 |
| **不放 iCloud** | Apple 5.1.3 明确"不得把个人健康信息存进 iCloud" —— 我们的云备份走**自家服务器**、密文存储，本来就不在 iCloud。⚠️ 但以后**不许**为了省事把云备份改到 iCloud/CloudKit |
| **不看历史** | 搭子只看"今天/最近 7 天"的摘要，**不给历史明细**（否则就是"我把训练数据交给你了"） |
| **可解释** | 搭子页上那行小字写清："你只分享了这些" + 一个「改共享范围」入口 —— 这比任何隐私政策都管用 |

## 五、合规门槛（做哪一层，就扛哪一层的责任）

| 层 | Apple（原文核对过） | 中国大陆（原文核对过） |
|---|---|---|
| **L0 邀请** | 无通用禁令：邀请码/邀请链接本身不违规（5.6.3 禁的是**刷榜/刷评/操纵推荐位**，与用户间邀请不是一回事） | 无（不产生用户间内容） |
| **L1 关系 + 结构化状态** | ① **1.2 用户生成内容四项 must**：过滤机制 / 举报入口 + 及时响应 / **拉黑滥用用户的能力** / 公布的联系方式。⚠️ 即"只有结构化数据"**也没有书面豁免**（未确定项），**不要赌**——把四项都做上，并在审核备注里写明"仅结构化打卡状态、无自由文本"；② **5.1.1(ii)+5.1.2(i)**：把用户数据展示给别人须**明确披露 + 明确同意**，按数据类别**分项**同意最稳；③ **5.1.3 健康/健身数据更严**：只能用于"改进健康管理"且须获许可，**不得存 iCloud**；④ 账号注销必须连带清掉搭子关系（5.1.1(v)）；⑤ **4.8 我们不触发**：用自建账号体系（邮箱 + 口令）落在"exclusively uses your company's own account setup"的豁免里，不需要 Sign in with Apple | ① 好友关系与共享字段属**个人信息**，向他人提供要**单独同意**（不能靠政策概括同意）；② 政策须**分项列明"共享给搭子的字段"**；③ ⚠️ **最可能被踩的一条**：《移动互联网应用程序信息服务管理规定》第六条 —— 提供**信息发布、即时通讯**等服务的，必须对注册用户做**真实身份信息认证**（**手机号 / 身份证号 / 统一社会信用代码三选一**），不提供真实身份信息不得提供服务；该规定第二条把"信息服务"定义得很宽（文字/图片/语音/视频的制作、复制、发布、传播）。**"结构化状态给一个搭子看"是否落入这个口径没有明文排除 → 未确定项，但风险是实的**。缓解：**手机号即可完成认证，不必强推身份证**；④ 同规定第八/十四/十六/二十二条还要求：内容审核机制 + **与服务规模相适应的专业人员**、涉舆论属性或社会动员能力的新功能做**安全评估**、公开管理规则与服务协议、**醒目的投诉举报入口与受理处置反馈**；⑤ **未成年人**：《未成年人网络保护条例》第三十一条（为未成年人提供信息发布/即时通讯须核实其真实身份，否则不得提供）、第二十六条（网络欺凌防治 + 屏蔽陌生用户/可见范围/禁止发送）、**第四十三条（网络社交服务须设"未成年人模式"：时段/时长/功能/内容 + 监护人管理）**、第四十四/四十五条（**分年龄消费限制** —— 这条与我们的会员付费**直接交叉**）；罚则最高可责令停业整顿 |
| **L2 推送** | **4.5.4**：推送不得是 App 运行的前提，且**不得推送敏感个人信息** → "搭子今天没练"这类健身信息**不许写进 payload**（只带通用 id，打开 App 再拉）；营销推送要显式 opt-in + 可退订 | APNs 在中国大陆可用（不需要厂商通道）；但国内安卓 **FCM 基本不可用**，要接华为/小米/OPPO/vivo 的厂商通道（通常要求**先上架对应商店并通过资质审核**），常见做法是接聚合推送（极光/个推）统一接入 |
| **L3 UGC/社区** | 1.2 四项 + 1.1.1 违禁内容 + 1.2 的兜底（屡犯可被移出开发者计划） | 实名 + 内容审核人员 + 安全评估 + 投诉举报 + 未成年人模式 + 备案信息变更 —— 一整套平台义务 |

> ⚠️ 上面那条国内实名是**这一页最需要你决定的前置条件**。它有两种结局：
> ① 结构化的一对一状态共享**不触发**实名 → 国内也能做搭子（但仍要补：投诉举报入口、管理规则页、未成年人模式、内容审核机制）；
> ② 触发 → 三条路：**(a) 国内先不做搭子**（iOS/海外先上）；(b) 国内要求绑定手机号（多收一类个人信息 + 政策与备案都要改）；
> (c) 只做"邀请 + 各自独立使用"（不建立双向可见关系，就不产生用户间信息发布）。
>
> **我的建议：(a)** —— 我们刻意只收邮箱，为了一个人际功能改成收手机号，隐私与备案代价都不划算；
> 而且真做国内社交，**未成年人模式 + 分年龄消费限制 + 内容审核人员**是法定配套，那不是"加个功能"的量级。
> 在查清之前，**不许把搭子写进国内版计划**。
>
> 📌 还有一条**与会员方案的交叉**：若国内做社交，就落入"网络社交服务"，必须设未成年人模式并提供
> **分年龄的消费上限** —— 这条要求同时压在**付费会员**上（已补进 `docs/plan-membership-2026-10-10.md` §7.2）。

## 六、搭子不该收费（与会员方案的关系）

* **搭子对双方免费**：被邀请的人如果是"为了回应朋友"才进来，却先撞上付费墙 —— 那不叫增长，那叫劝退。
* 搭子的价值在于**留存**（D30），而留存是付费转化的前提；把它做成付费功能等于把漏斗最上面那一截掐掉。
* 与会员方案的接口：Ultra 的**云备份**与搭子无关（搭子同步的是几十字节的状态，不占配额、不进备份）。
* ⚠️ **不做"邀请送会员"**（邀请 1 人送 1 个月 Ultra 之类）：一旦邀请与付费权益挂钩，
  就落入内购与促销条款（3.1.1 / 5.6.3），审核风险陡增；而且会招来刷邀请的灰产。
  搭子的激励靠"关系本身"，不靠发权益。

## 七、冷启动：邀请本身就是最大的获客漏斗

我们现在的获客只有一条：**训练完生成分享卡 → 微信**（`PRODUCT.md` §4 唯一社交形态）。
搭子把它从"一张图"升级成"一张图 + 一个能落地的邀请码 + 一个真的会回你消息的人"：

1. 总结页多一行「邀请搭子一起练」→ 分享卡带上邀请码；
2. 对方在落地页看到的是"某某邀请你一起练"（只有昵称，没有训练数据 —— 落地页是公开的，别泄露）；
3. 装好后输码 → 建立关系 → 双方开始互相看见。

**判据**：邀请链接落地页不出现任何训练数据；邀请码在落地页只用于"装完填进去"，不用于解锁任何东西（与会员的兑换码是两码事，别混）。

## 九、分阶段与工时（建议排在会员之后）

| 阶段 | 内容 | 工时 | 前置 |
|---|---|---|---|
| **L0** | 邀请码 + 带码分享卡 + 落地页 | 2–3 人日 | 复用会员方案的码体系（建议一起做，省一遍服务端） |
| **L1** | 搭子关系 + 结构化状态 + 站内通知 + 分享范围与同意门 + **最小 UGC 四件套**（举报/拉黑/管理规则/联系邮箱） | 6–8 人日 | 政策与商店表单改完 |
| **L2** | 推送催办（iOS）+ 限频反骚扰 | 4–6 人日 | APNs 配置；**国内另算**（厂商通道或聚合推送，通常要求先上架对应商店） |
| **L3** | 社区/动态/聊天 | ❌ 不做 | —— |
| 合计 | | **12–17 人日**（做到"能互相看见 + 能催"） | |

## 十、风险

| 风险 | 处置 |
|---|---|
| **"搭子"变成"互相看见对方没练"的压力**，反而掉留存 | 文案克制：不写"你落后了"；只在**连续断 2 天**时提醒；提供"暂停共享"（生病/出差） |
| 搭子关系链冷启动失败（朋友不装） | 邀请码落在分享卡上，跟着现有的分享路径走；不做"必须加好友才能继续用" |
| 国内实名要求（§五 待核实那条） | 查清再定；必要时国内不发这一步 |
| 数据泄露面扩大（服务端多了一张"谁和谁是搭子"的表） | 只存账号 id 与结构化事实，**不存训练明细**；不存昵称（昵称在客户端本地）；日志不打账号 |
| 审核被当成"未声明的社交功能" | 商店表单"是否含社交/UGC"如实改（L1 = 含用户间互动，但不含公开内容）；审核备注写清"1:1、无自由文本、无公开广场" |

## 十二、必须由你（或律师／后台）亲自核实的 8 条

| # | 要核实什么 | 为什么只能你来 |
|---|---|---|
| 1 | **"结构化训练状态共享给一个搭子"是否构成《移动互联网应用程序信息服务管理规定》第六条 / 《互联网用户账号信息管理规定》第九条的"信息发布、即时通讯"** | 法条没列举排除，**这一条决定国内实名是否强制**，也决定国内做不做。建议按"可能构成"来设计（手机号实名即可，不必身份证） |
| 2 | 个人开发者能否以"**社交类**"业务类型通过 **APP 备案**，是否需要**变更备案** | 工信部备案是强制前置，个人也在范围内；"安卓/iOS 双端分别备案""业务类型细分"目前只见到二手整理，**以通信管理局口径为准** |
| 3 | 是否被认定为"**具有舆论属性或社会动员能力**"→ 是否需做**安全评估**（MDI 第十四条） | 这是"要不要额外做一次评估"的分水岭，没有公开的自查表 |
| 4 | 搭子的健身数据共享在 **PIPL** 下是否属**敏感个人信息**、是否需**单独同意**（而非概括同意） | 涉及法律判断；我们按"是"来设计（分项单独同意），但要你确认口径 |
| 5 | Apple 是否接受"**仅结构化数据、无自由文本**"从而不需要完整 UGC 四件套 | 我按"**不接受豁免**"设计（四项都做）；若你想省事，需要预审沟通或实测 |
| 6 | **Google Play** 的 UGC 政策逐字要求 | 这次抓不到那个页面（超时），**没有逐字核对**，上 Play 前自己读一遍 |

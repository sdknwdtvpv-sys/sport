### ⑦ iOS「液态玻璃」：已拍板 A（仅 iOS）+ spike 结论（2026-10-06）

**决定**：走 **A 原生真材质**、**只做 iOS**；Android 一个像素都不动。
**载体**：**自己写一个 platform view**（约 100 行 Swift + 一个 Flutter widget），
**不引第三方包** —— 与本仓库一贯做法一致（通知/Live Activity/休息提示都是自己写的桥，
当初为的是"多一个依赖就多一条要维护、要如实说明的东西"）。A 路线里 pub 上那两个包
（`native_liquid_glass` 未验证发布者 · `liquid_glass_renderer` 自标 experimental）
在我们只需要"一块玻璃"的场景下都不划算：**不引依赖 = 政策 SDK 表 / 两张商店表单 /
隐私事实表 / `collection-live` 清单一个字都不用改。**

**SDK 事实**（本机 Xcode 27.0 / iPhoneSimulator27.0.sdk 头文件实读）：
`UIGlassEffect : UIVisualEffect`（`API_AVAILABLE(ios(26.0))`）有 `+effectWithStyle:`（`.regular` / `.clear`）、
`isInteractive`、`tintColor`；另有 `UIGlassContainerEffect`（多个玻璃元素合并、`spacing`）；
圆角走 `UIView.cornerConfiguration`（`UICornerConfiguration`）。本机**没装 CocoaPods**，
所以桥要跟着现有工程走 **SPM**（与 `ReminderBridge.swift` 那批一致）。

**spike 实测（两张证据图，同一块 `UIGlassEffect` 只换背后的东西）**：

| 背后是 | 观感 | 证据 |
|---|---|---|
| **纯炭黑 `#101014`** | ❌ **一块浅灰板** —— 比屏幕上所有东西都亮、抢视线，完全不像玻璃 | `docs/images/legacy-5tab/glass-spike-1-flat-vs-content.png` |
| **暗 + 纹理/辉光**（炭黑 → `#1D1B26` → `#2A1A16` + 橙色辉光） | 🟡 `.regular` = 像"烟熏玻璃"，可用；**✅ `.clear` + 淡橙 `#FF5A1F33` = 最好看**，暗底上仍读得出是玻璃 | `docs/images/legacy-5tab/glass-spike-2-dark-textured.png` |
| **彩色内容**（渐变 + 卡片） | ✅ 就是 Apple 那个样子：吸色、亮边、跟着内容动 | 同上 |

**由此定下三条落地规矩**（写在这里，免得实现时凭感觉）：
1. **玻璃只在"背后真的有内容经过"的地方用** —— 滚动列表/卡片/图片/彩色元素的后面。
   最典型的就是**底部 Tab 栏**（内容从它下面滚过去时才是它最好看的时候）；
2. **纯色空屏上不要用 `.regular`**（会变灰板）；那里要用就 `.clear` + 极淡的 tint，
   或者干脆不用（`Screens` 那种设置页就是这一类）；
3. **训练屏不碰**（每秒跑休息计时 + 大按钮，"一组=一次点击"的红线区）。

**未验的两件事（如实记）**：① iOS **26 以下**的退回形态没验过（本机只有 iOS 27 运行时；
桥里写的是 `UIBlurEffect(.systemUltraThinMaterial)`）；② **真机 release 的帧率**没测 ——
platform view 有整屏合成代价，package 文档与 Apple 文档都这么说，必须上真机测过再铺开。

**落地顺序**：① 桥 + 一个 Flutter widget（`GlassSurface`，`UiKitView`，iOS 26+ 真材质、
<26 退回系统材质、非 iOS 直接返回 child 或占位 → **Android 完全不变**）；
② 先只接**底部 Tab 栏**一处，真机 release 看帧率与观感；③ 过了再看弹层/Sheet；
④ 界面一改，**三套截图 + 软著说明书要重出**（`docs/screenshots.md` 里那套流程）。

## 〇之二、**账号体系：推迟到有盈利之后**（2026-10-06 用户拍板）

> ⚠️ **这一条已被 2026-10-06 同日晚些时候的新拍板覆盖**：用户点单 **P1-3 做**，并且是
> **"必须先登录才能用"**。方案与代价（15 处承诺落点、服务端身份、应用内注销、两条正面冲突）
> 全在 `docs/plan-account-login.md`。**下面这一节留作历史**，不要再按它执行
> （尤其是那句"别在它被重新提起之前提前做" —— 它已经被重新提起过了）。

> 原话：「**给用户看的要登录一个账号**」→ 追问成本后：「**如果要花钱的话，就先不做，
> 等项目有了盈利之后再做**」。

**决定：现在不做。** 记录在这里是为了两件事：① 别忘了它；② **别在它被重新提起之前提前做**。

### 为什么它是"要花钱"的那一类（三条路各自的价签）

| 路线 | 花钱在哪 | 量级 | 现在能不能做 |
|---|---|---|---|
| **邮箱 + 口令** | **几乎不花**：服务端已有（`api.elliotli.work`）+ 复用一个邮箱的 SMTP（登录验证码量极小，免费额度足够）；**没有认证费、没有许可费** | ¥0 | ✅ 能（这是唯一零成本的路） |
| **手机号 + 短信** | 短信通道（阿里云/腾讯云）：签名与模板审核**几元**，之后**按条计费**（月发几百条 → 一年几十到几百元） | ~¥100–500/年 | 🟡 能，但要开户 + 备案主体 |
| **微信登录** | 开放平台**开发者资质认证**（社区口径 **300 元/次、按年续**） | ~¥300/年 | ❌ 还要先有**已上架应用**才能提审 |
| **Sign in with Apple** | 没有单独费用，但它**必须配付费 Apple Developer 账号**（¥688/年）—— 而那个账号**上架本来就要买**（见 `docs/your-todo.md` 第 5 条） | ¥688/年（已列在上架预算里） | ⏸ 等付费账号 |

⚠️ 一条容易混的账：**¥688/年的 Apple 开发者账号不是"登录的代价"** —— 它是**上架**的代价，
上架那天就得买（付费档才能 TestFlight/Ad Hoc/提审）。所以"为了省登录的钱而不买它"不成立；
反过来说，**买它的理由应该是上架，不是登录**。

### 一条技术底线（真做时不许丢）

**登录给用户看，但服务器仍然读不到他的数据。** 现在的云备份是
"恢复码 → HKDF → 密钥 → 哈希成 `account_id`，服务端只存密文"；
加账号只需换"密钥从哪来"（口令派生），**不必**让服务端能解密。
一旦为了省事让服务端能读，政策里「服务端只拿到密文」整句就作废了 —— 那是改产品性质，不是加功能。

> `index`（第几个动作）与 `restEndsAtMs`，**没有记"这个动作已经记到第几组"**；
> 恢复时 `_trainSession` 建的是一个**全新控制器**（`_setSeq` 从 1 开始），
> 也不把库里已有的组读回界面。组 id 是 `s_<workoutId>_<exerciseId>_<setSeq>`
> —— `setSeq` 从头数，就撞上了原来的第 1 组（upsert 静默覆盖）。
>
> **为什么它值得马上修**：① 是**数据丢失**，而项目自己写着"数据丢失是工具类死刑"；
> ② 它长在 v1.35.0 的卖点「训练中断不丢状态」上 —— 用户一次中断就会踩到，
> 而**症状是"总数没变"，不做前后对比根本看不出来**。
>
> **修法（已完成，v1.37.1）**：`WorkoutController` 新增 `alreadyLogged` ——
> 调用方把 `store.setsFor(workoutId)` 里这个动作的组传进来，据此恢复已完成列表、
> `_setSeq`（取最大值，热身也占号）与计划进度。**刻意不在 `ActiveSession` 的 JSON 里存计数器**：
> 组本来就逐条落库，数据库才是真源。顺带修了同一条路径上的第二处（恢复时没带 `startedAtMs`，
> 总结页时长会只剩后半段）。
> **验收**：4 条回归测试（把修复临时撤掉会红 3 条）+ 真机同流程走一遍（2 组 → 杀进程 → 继续 →
> 第 **3** 组 + 2 行已完成 → 记一组后「我」页 **3 组 / 960 kg**）。
> 证据图 `docs/images/legacy-5tab/p0fix-01-resume-shows-set-3.png` · `p0fix-02-after-logging-3-sets.png`。

### ③ 训练结束提醒：施工清单（2026-10-05 侦察 → **同一天做完**）

> ✅ **这一节已全部落地**（`docs/feature-backlog.md` §〇 第 6 条）。清单留在这里，是因为它记着
> **当初为什么这么做**（尤其"复用同一个排程位、不新开通知位"那条取舍）。
> 落地时的两处修正写在最后面。

**底座已经有了，不要重写**：`features/profile/reminder_service.dart` 的 `sync()` 就是
"把系统里的排程同步成【当前设置 + 今天的事实】该有的样子"，而且它**已经在三个时机被调用**
（开 App / 练完一次 / 用户改设置）——「练过就不打扰」那条逻辑现成。`reminder.dart` 管文案与
"下一次什么时候响"的纯计算，`ReminderScheduler.kt` / `ReminderBridge.swift` 管平台侧。

要做的是**在它旁边加一条一次性的"训练后提醒"**：

1. **文案**：✅ 已做（2026-10-05）—— `features/profile/next_training_copy.dart`，「明天该练背了 / 点开直接开始」，
   3 条测试（含"没有下次部位就返回 null、不编"与"不催"）；
2. **时机**：总结页出现时（`_trainSession` 返回之后）排一条**一次性**通知；
   复用现成的排程通道（**不新增权限**）；
3. **取消**：用户当天再练 → 走 `ReminderService.sync()` 顺手撤掉那条（同一个出口，
   否则会出现"已经练过了还提醒你练"）；
4. **合规**：`privacy-policy.md` / `.en.md` 的 `POST_NOTIFICATIONS` 行与那段"说明五点"

5. **测试**：文案纯函数（含"没练过就不该有下次部位"）、排程/取消的幂等、
   "练完一次就把今天那条撤掉"、以及**通知不新增权限**这一条（manifest 权限数不许变）。

**落地时改掉的两处（与上面清单不同，以这里为准）**：

- **第 2 条"排一条一次性通知"改成"同一个排程位换一句话"**：两个平台的真身都只有**一个**
  排程位（Android 一个 `requestCode`、iOS 一个 `requestId`），而"下次该练了"本来就是同一件事。
  于是判断收进一个纯函数 `composeReminder`：练完 + 说得出下次部位 + **那个点今天还没到**
  → 今晚那条说「明天该练X了」；否则**一字不改地退回**通用那条（"今天还没练"）。
  "那个点已经过了就退回"是刻意的：预告顺延到明天，"明天"就成了假话。
- **第 3 条"取消"不需要单独做**：`sync()` 本来就是唯一出口（先撤再排），
  当天再练/再改设置都会重新算一遍 —— 状态是**推导出来的**，没有第二处真相要维护。
- **新增一处纪律**：`_trainSession` 出口那句必须 `unawaited`（见下面的断点）。
